# 反模式：角色夹具坏了，三种角色的用例照样全绿

> 来源：touch2-engine 收件箱空态修复（TOU-1448，2026-11-27）
> 结果：「三种真实成员身份」那组 e2e 从写好那天起，没有一次真正切换过角色；直到一个新改动要求负责人看到不一样的东西，才红出来

## 一句话结论

按角色分支的用例，至少要有一条断言是「**不同角色看到的东西不一样**」。只给每个角色各断言一遍「页面正常」，夹具一旦退化成「所有角色都一样」，整组还是绿的。

## 场景

- 页面按角色（负责人 / 成员 / 独立业务员）渲染不同内容
- e2e 用一份夹具造出几种角色的用户，每种角色跑一遍同一组断言
- 服务端拿不到角色时有兜底（按「无角色」或最低权限渲染），不报错

## 踩坑经历

夹具里租户、用户、成员的 id 后缀只写了 20 位，而 id 规范要求 21 位。

服务端解析团队身份的函数在这些 id 上直接抛错。页面拿不到角色，走了兜底，**三种角色一律按「无角色」渲染**。

这组用例断言的都是三种角色共有的东西：收件箱打得开、列表渲染了、空态文案在。所以三条全绿。

出问题是在一刀新改动里：要求负责人看到「去连接页给邮箱指定主人」，成员看到「请负责人去指定」。负责人那条断言第一次真正依赖了角色，CI 上红了。

排查时先怀疑的是新改动的判断逻辑，改了一轮没用。最后用临时真库探针去读夹具造出来的身份，才看到角色是空的。夹具 id 改合规之后，探针读到的角色是：
- 负责人：2 人；
- 成员：1 人；
- 独立业务员（只有自己一个人的负责人）：1 人。

都对了。

## 为什么会漏

- **兜底把错误吞成了合法状态**：「无角色」本身是页面支持的一种渲染，不是报错页。测试看到的是一个正常页面。
- **断言只覆盖交集**：每个角色各断言一遍「共有的东西都在」，正好是兜底状态也满足的那部分。
- **夹具错得很隐蔽**：差一位的 id 肉眼看不出来，类型检查也查不出来，因为它们都是字符串。

## 改法

1. 按角色分支的那组用例里，加一条**区分性断言**：负责人看得到、成员看不到的东西（或者反过来）。夹具一旦退化，这条先红。
2. 夹具造完身份后，在用例开头**断言一次角色本身**（从页面或接口读出来，和期望的角色比），不要默认夹具造对了。
3. 夹具里的 id 用产品自己的 id 生成函数造，不要手写字面量。
4. 服务端解析身份失败时，测试环境下应当打日志或报错，不要静默兜底。
