# 反模式：出版前检查只核结构，不核渲染器实际接受的类型

## 一句话结论

"检查通过、渲染才炸"说明检查器和渲染器各有一份契约，而且检查器那份更宽。检查规则要按**渲染器真正接受的输入**来写：渲染器只吃字符串的地方，检查就要断言是字符串，而不能只核"列数对不对"。改完后把每种块类型都喂一遍渲染器，作为冒烟测试。

## 场景

报告、文档或配置走"内容 JSON → 检查脚本 → 渲染脚本"的流水线：

- 检查脚本是后来补的，按"写作纪律"来设计：章节齐不齐、引用有没有登记、表格列数是否等于表头；
- 渲染脚本是先写的，对某些字段有隐含的类型假设（例如表格单元格只接受 `str`）；
- 内容里有一种看起来合法的写法，比如在单元格里放富文本 `["文字", "bold"]`，因为正文段落支持富文本。

## 踩坑经历（2026-11-23，个人深度报告技能 trade-deep-report）

三份报告的 `report.json` 都过了 `check.py`。渲染时其中一份在 `docx_kit._cell_text` 里报错：

```
ValueError: too many values to unpack (expected 2)
```

原因：采购表有一行写成了 `[R("8544 绝缘电线、线束","bold"), R("571","bold"), "…"]`，单元格是 `["文字","bold"]` 这样的二元列表。渲染器把它当成"分段列表"逐段解包，拆到字符串就崩了。第一次的修法是再套一层 `[[...]]`，换来另一个错：

```
AttributeError: 'str' object has no attribute 'get'
```

表格单元格的渲染代码期望的是 `(text, opt_dict)`，和正文富文本 `(text, style_str)` 的形状并不一样。也就是说，单元格压根就不支持富文本。前后两轮报错都发生在 docx 阶段，PDF、HTML 跟着没出；同一批的另外两份报告则已经生成，三份成品的版本因此对不齐。

## 根因

1. **检查器的契约是从"写作规范"推出来的，渲染器的契约藏在实现里。** `schema.md` 只写了"每行列数必须等于表头"，没写单元格的类型。检查器照文档实现，于是所有"列数对、类型错"的输入都能通过。
2. **同一个词在两处含义不同。** 正文的"富文本"是 `[[文字, 样式字符串], …]`，单元格内部的分段则是 `[(文字, 选项字典), …]`。写内容的人（包括模型）会把正文的写法类推到表格。
3. **报错只能当一次性的修复提示来读，没有回写成检查规则。** 不补规则，下一份报告还会踩同一个坑。

## 正确做法

1. **把渲染器的类型假设上提到检查器。** 本例在 `check.py` 的表格分支里加了：
   ```python
   for r, row in enumerate(b.get("rows", []), 1):
       if any(not isinstance(x, str) for x in row):
           E.append(f"{where} 第 {r} 行有非字符串单元格(表格单元格只支持纯文本)")
   ```
   并在 `schema.md` 的表格说明里写明"单元格只支持纯文本字符串"。
2. **用反例验证新规则真能拦住。** 拿一份已通过的 JSON，把单元格改成 `["x","bold"]`，确认检查会报错，同时两份样例 JSON 仍然通过，确认没有误伤。
3. **加一个覆盖全部块类型的最小渲染冒烟测试。** 每种块类型各放一个，每种字段取其允许的各种形状（字符串 / 富文本），跑一次完整渲染。检查器放过、渲染器拒绝的形状，在这里会第一时间暴露。
4. **渲染器报类型错时，先确认它到底接受什么形状，再动内容。** 本例第一次"再包一层"是按报错猜的，又多绕了一轮。

## 适用范围

- 适用于："内容 → 校验 → 生成"三段式的流水线，包括报告生成、模板渲染、IaC 渲染、静态站点构建。
- 不适用于：校验和渲染共用同一份 schema 定义（例如 pydantic 模型同时驱动两端）。那种情况下契约本来就是一份，不会分叉。
