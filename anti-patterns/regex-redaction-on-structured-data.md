# 反模式：用文本正则给结构化数据脱敏——遮掉了字段名，放过了值

## 一句话结论

在 `{"key": "PASSWORD", "value": "<真密码>"}` 上跑 `(password|secret|key)[\s":=]+(\S+)`，命中的是**标签**不是**值**——输出满屏 `<已遮蔽>`，看起来完全正常，唯独真正该遮的那个是明文。**脱敏的正确性没有任何反馈信号**：遮多了、遮错了、一个没遮，输出长得一模一样，所以"能不取的就不取"永远优于"取了再遮"。

## 场景

- 从 API / 配置中心 / 环境变量里读一批 `{name, value}` 结构，想打印出来看结构，又怕带出凭据
- 顺手写个正则扫一遍序列化后的文本
- 输出里有一堆 `<已遮蔽>`，于是判定脱敏生效，把结果贴进对话、日志、issue、聊天群

## 踩坑经历

某 B2B 获客项目做数据库备份外置（2026-08-04）。需要看生产 Postgres 的环境变量，判断连接串的形状、以及有没有对外端口。变量里含密码，所以给探针脚本写了脱敏：

```python
SECRET_RE = re.compile(r"(password|secret|token|key)([\"'\s:=]+)([^\"'\s,}]+)", re.IGNORECASE)
text = SECRET_RE.sub(lambda m: f"{m.group(1)}{m.group(2)}<{len(m.group(3))} 字符已遮蔽>", text)
```

而 GraphQL 返回的形状是：

```json
{"variables": [
  {"key": "PASSWORD", "value": "<32 位真密码>"},
  {"key": "POSTGRES_USER", "value": "root"}
]}
```

正则在 `key": "PASSWORD` 上命中，group(3) 是 `PASSWORD` 这个**字段名**，于是把标签遮成了 `<8 字符已遮蔽>`，而紧挨着的 `"value": "<真密码>"` 里没有任何触发词，**原样打了出来**。

输出长这样：

```
{"key": "<26 字符已遮蔽>", "value": "postgresql://${USER}:<已遮蔽>@${HOST}..."}
{"key": "<8 字符已遮蔽>",  "value": "Xk7pQ…（32 位随机串，明文，此处为示意值）"}
```

第二行看着和第一行一样"已处理"。生产库密码因此进了对话与终端 scrollback，只能轮换。

**更值得记的是它为什么骗得过人**：连接串那一行的密码**确实**被遮住了（因为 `://user:pass@` 那条独立的规则起了作用），所以输出里既有正确遮蔽的样本、又有失败的样本，视觉上完全无法区分。有一部分生效，比全都不生效更危险。

## 为什么会写成这样

序列化之后再处理，是因为"一次搞定所有嵌套结构"看起来更省事——不用管数据是列表还是字典、嵌套几层。但代价是**把类型信息全丢了**：正则看不出哪个 token 是 key、哪个是 value，只能靠"离触发词最近"这种位置启发式，而 `{"key": ..., "value": ...}` 这种把字段名本身当数据的形状，恰好让位置启发式失效。

这类形状在配置系统里非常常见（K8s env、GitHub Actions、各家 PaaS 的变量 API），不是罕见边角。

## 解法

1. **按结构处理，别扫文本**。遍历 `{key, value}`，用 key 名决定 value 遮不遮：

   ```python
   SENSITIVE_KEY = re.compile(r"password|secret|token|credential|_key$|^key$", re.I)

   def redact_value(key, value):
       if SENSITIVE_KEY.search(key or ""):
           return f"<{len(value)} 字符已遮蔽>"
       ...
   ```

2. **加一条不看名字的兜底**。名字可能叫任何东西，但高熵长串就是不该出现在日志里：

   ```python
   if len(value) >= 20 and re.fullmatch(r"[A-Za-z0-9+/=_\-]+", value):
       return f"<{len(value)} 字符疑似凭据，已遮蔽>"
   ```

   会误伤路径之类的东西（实测把 `/var/lib/postgresql/18/docker/pgdata` 也遮了），**接受这个代价**——看不清一个路径的成本，和漏一把密钥的成本不在一个量级。

3. **脱敏函数必须有测试**。塞一条已知的假密码进去，断言它不出现在输出里。这是唯一能给"到底遮住了没有"提供信号的办法——**否则你永远只能靠肉眼看输出"像不像已脱敏"，而这次证明了肉眼看不出来**。

4. **最重要的一条：先问"我到底需要看什么"**。这次真正需要的只有「连接串的结构」和「有没有对外端口」，**值一个都不需要**——本可以只打 key 名和 `len(value)`，根本不碰值，脱敏这段代码压根不用存在。

   **取了再遮是在给自己出一道每次都必须做对的题；不取则是把题删掉。**

## 适用范围

- 适用于：任何要把配置 / 环境变量 / API 响应打印出来给人看的场合，包括调试脚本、CI 日志、给 AI 看的探针输出
- 尤其适用于：`{name, value}` 这种**把字段名当数据**的形状（K8s env、CI 变量 API、各家 PaaS 的配置接口）
- 不适用于：值本身就是要处理的对象（比如做凭据轮换），那种情况该做的是不打印，而不是脱敏
