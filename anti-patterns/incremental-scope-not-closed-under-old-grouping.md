# 反模式：增量重算的"受影响集合"只沿一种邻接扩展

## 一句话结论

增量重算要覆盖的集合，必须同时对**新的分组关系**（本轮簇成员）和**旧的分组关系**（上一 run 的 parent 分组）做闭包，直到不再增长。只从"变更行"出发沿一种关系扩一跳，会漏掉"被拉走成员后剩下的旧簇兄弟"——它们没有变更、不在新簇里，但旧的簇级字段（parent_id / cluster_size）已经作废，留在库里就是全局不变量破坏，而按 scope 做的校验永远是绿的。

## 场景

- 结果表带簇级派生字段（parent_id、cluster_size、簇级关联结果），全簇行必须一致
- 增量只重算"受影响簇"并只回写 scope 内的行
- 校验（I-0/I-2/I-3）按 scope 过滤运行

## 踩坑经历

2026-08-29 企业样本去重 Task 18。plan 的公式是 `A = (changed ∪ removed) 的旧簇 ∪ (new ∪ changed) 的当前簇`——changed/removed 触发的拆簇覆盖了，**new 触发的拆簇没有**：新增行 n 与老簇 {N1, N2} 的 N1 相似并簇，S2.5 锚定把 N1 带走、N2 落到别的簇；touched={n} → A 只含 {n, N1} 的新簇，N2 的行既不在 scope 也没被重写，仍指向 parent=a、cluster_size=3。回写后同一 parent 下 cluster_size 2 与 3 并存，scope 校验全绿。spec 其实写了"拆出的子簇都进 A"，plan 把它翻译丢了。

## 正确做法

- A 做不动点：`scope ← A 的当前成员` → `扩：prev 中与 scope 任一行同 parent 组的全部行` → `映射回它们的当前簇` → 重复到不增长（通常 2 轮）
- 加一条独立守卫而不是信任推导：`prev parent 组与 scope 相交但未被完全包含的行数 == 0`，否则拒绝回写——它与推导用同一判据但由不同代码路径算出
- 测试要有"新增行触发拆簇"的用例，断言对侧旧簇兄弟也进 scope 且结果一致；scope 断言用等值而不是子集
- scope 内的 I-0 几乎是空校验（scope 本身由 A 推导），别把它当作兜底
