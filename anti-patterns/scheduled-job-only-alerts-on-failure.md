# 反模式：给定时任务只配「失败告警」——最危险的两类失败它一条都覆盖不到

## 一句话结论

定时任务有三类失败：**跑了失败 / 根本没跑 / 跑了成功但产物是空的**。失败告警只覆盖第一类，而那恰好是三类里最不容易出事的一类——因为它至少还有个信号。后两类都是**静默**的，且只会在你真正需要那个产物的那天被发现。看门狗必须**独立于被监控的任务**，判断依据必须是**产物**而不是运行记录。

## 场景

- 备份、对账、报表、数据同步、证书续期、清理任务——任何"平时不产生被使用的产物"的周期性工作
- 配了 CI 失败通知 / 邮件告警，就认为监控做完了
- 应用挂了五分钟就有人喊，这类任务断了三个月都不会有人发现

## 三类失败

### ① 跑了，失败了

进程非零退出。这类**最容易覆盖**，也是唯一被失败告警覆盖到的。

覆盖它的前提是任务本身把各种异常变成硬错误。以数据库备份为例，至少要挡住：

- `pg_dump | gzip` 的退出码默认取**最后一个命令**——dump 挂了 gzip 照样成功，留下一个 0 字节的 `.gz` 而整条流水线全绿。必须 `set -o pipefail`。
- 恢复演练用 `psql` 导入时，**psql 默认遇错继续、最后仍以 0 退出**。少了 `-v ON_ERROR_STOP=1`，"恢复演练"就是一道永远绿的装饰。
- 上传对象存储拿到 HTTP 200 只说明请求被接受了，要回读比对 sha256。

这三处的共同点：**它们失效时整条链路仍然全绿**，所以必须**单独测试它们真的会挡住失败**——正常路径通了什么也证明不了。

### ② 根本没跑

**比 ① 隐蔽得多，而且失败告警一条都覆盖不到**——没有 run，就没有失败，就没有通知。静默来源至少三个：

- **GitHub 会自动禁用 60 天无提交仓库的 scheduled workflow**（官方行为，只发一封邮件）。低活跃度的仓库最容易中，而低活跃度恰恰意味着更没人盯着。
- `cron` / `schedule` 不保证准时，平台高峰期会延迟甚至丢。
- 有人改坏了 cron 表达式、误删了任务、或者关掉了整个 workflow。

### ③ 跑了，成功了，但产物是空的

**最阴的一类**。校验挡得住"0 字节"，但挡不住**合法的空产物**。

实测形态：库连上了、schema 是空的、`pg_dump` 正常返回 401 字节、恢复演练报告"恢复后用户表数量：0"、上传成功、sha256 比对通过——**全绿**。

空库时这是正确行为。但生产库有数据之后，一份突然缩回 400 字节的备份意味着出了大问题，而**所有检查都会放行**。

## 解法

**① 失败告警**：推到一个人真的会看的地方（IM 群，不是邮件——邮件和几十封 CI 通知长得一模一样），带失败步骤和运行链接。

**② 独立看门狗**，两条设计要求，缺一条就等于没做：

- **不能跑在被监控的任务里**。同一个 workflow 没跑的时候，塞在里面的检查同样不会跑。它必须是独立的触发源（另一个 workflow、云函数、外部的 cron 监控服务、甚至一台常开机器上的 crontab）。
- **判断依据是产物，不是运行记录**。问"对象存储里最新的备份是什么时候的"，而不是"任务最近一次运行成功了吗"。前者证明**产物真的存在**，后者只证明**有个任务跑过**——在 ① 的场景下这两件事会分叉。

**③ 产物合理性**：与上一次比对，**大小骤降超过阈值（如 50%）就告警**。顺带记录业务量指标（表数、行数、记录条数），归零同样是信号。

**④ 每一类告警都必须被人为触发过至少一次。**

这条是核心，不是形式。删掉最新的产物，看门狗响了吗？把任务改成必然失败，通知到了吗？**没被触发过的告警等于没有告警**——它和"配置好了但其实没生效"在外观上完全一致，而你要到真出事那天才会知道是哪一种。

## 顺带：验证"我的监控真的在监控"

这三类失败的共同点是**信号缺失**，而不是信号错误。诊断信号缺失只有一个办法：**制造故障，看它响不响**。

同样的思路适用于任何"平时安静"的机制——降级逻辑、重试、熔断、限流、审计日志。它们的共同点是：**正常情况下你观察不到它们工作，所以也观察不到它们停止工作。**

## 适用范围

- 适用于：备份、对账、报表、数据同步、证书续期、缓存预热、清理任务
- 尤其适用于：产物平时不被读取的任务——**产物被频繁读取的任务自带监控**（没数据了下游立刻报错），而备份类的没有
- 不适用于：结果立刻被消费、失败当场可见的任务（比如 CI 构建本身）
