# 反模式：网页用两个 `<audio>` 并行播伴奏与旋律、靠 JS 追赶同步——手机上必断续，补丁越打越像拉锯

## 一句话结论

两条流各自缓冲、各自停顿，JS 每帧比对两个 `currentTime` 再用硬 seek / 变速去追，桌面能用，手机（Safari、微信内核）上就是"时断时续"。两轮补丁把参数调到极限、自动化同步测试 5/5 全绿，用户真机照样卡，项目因此搁置两个月。根治不是再调参数，而是把原生 App 之所以流畅的那个东西搬回网页——**一个解码器一条流**：服务端把伴奏和旋律预先混成单文件，播放器用一个 `<audio>` 在「伴奏 / 预混 / 纯旋律」三个来源间切换。

## 场景

- 练歌 / 跟练类页面：伴奏轨 + 引导旋律轨（或人声示范轨）可独立开关、独立音量
- 两轨是两个独立 MP3，用两个 `HTMLAudioElement` 同时 `play()`，其中一轨可能再绕道 Web Audio 做增益
- 目标用户主要在手机上用，且很可能是微信内嵌浏览器

## 详细说明

### 踩坑经历（声伴 shengban.aimusic.art，2026-07 → 2026-09）

播放器最初是双轨并行：伴奏为主时钟，主旋律轨常驻跟播（关闭时静音），一个 rAF 循环算 `drift = melody.currentTime - accomp.currentTime`，小偏差变速缓拉、大偏差硬 seek。桌面一切正常。

用户反馈手机上打开旋律后断续。7 月两轮修：

1. 伴奏 `waiting` 时旋律同步暂停、`playing` 时对时恢复（主时钟停摆期零校正）
2. 硬 seek 节流 ≥1.5s；变速幅度 ±8% → ±3%（±8% 在移动端有可闻水音）
3. 变速进出加迟滞带（>0.10 进 / <0.05 出），`playbackRate` 只在目标值变化时赋值（iOS 重复赋同值会重初始化时间拉伸器产生周期性咔哒）
4. AudioContext `statechange` 看门狗：iOS 会随时把上下文置为 suspended，走增益通路的旋律整段静音

每一条都对应一个真实症状，Playwright 双轨同步测试 5/5 通过。用户真机复测：还是卡。然后没时间了，放下。

9 月重看：原生 App 时代同样两轨为什么流畅？因为文件整份下载到本地（彩虹表解密要求完整文件）、系统原生解码器在同一硬件时钟上起播。网页版两样都不占——边下边播的流 + 浏览器媒体管线，两条流各卡各的，再让 JS 去追。**问题不在同步算法，而在"有两个时钟要同步"这件事本身。**

### 替代方案：服务端预混 + 单流三源

- 离线用 ffmpeg 把每个调的伴奏 + 主旋律混成一个 192k MP3：`amix=inputs=2:duration=first:weights='1 1.6':normalize=0,alimiter=limit=0.95:latency=1`（旋律 1.6 倍等于旧播放器滑条默认值；`latency=1` 补偿限幅器前瞻延迟；`duration=first` 以伴奏为准，旋律前奏静音段原样保留）
- 后端多一种文件类型只读本地目录；tones 接口在文件存在时返回 `mixFileUrl`
- 播放器只有一个 `<audio>`：伴奏开旋律关 → 伴奏文件；旋律开 → 预混；伴奏关旋律开 → 纯旋律文件；换源时记下 `currentTime / isPlaying / playbackRate`，新文件 `loadedmetadata` 后恢复。换源期间 `onTimeUpdate` 冻结在切换前的值，避免元素归零把光标拉回开头
- 删掉的东西：第二个元素、Web Audio 增益、AudioContext 看门狗、整个漂移校正循环。留下的：`currentTime` 瞬时回退护栏、A-B 循环、iOS 解锁
- 旋律音量从连续滑条降级为开关（混音比例固定）——用户接受，不接受则每档一份文件

### 顺带踩的坑

- **ffprobe 的头部时长不可信**：旧渲染批次 MP3 的 `format.duration` 比实际解码短 0.1–0.3s，用它校验"混音时长 = 伴奏时长"会大面积误判；必须完整解码（`ffmpeg -i x -f null - -progress pipe:1` 取最后的 `out_time_us`）
- 下载脚本按 URL 是否含 `.mp3` 定扩展名，1515 个 `.mpeg` 结尾的链接被存成 `.audio`，还有一个 `.audio.mp3` 双扩展名——按内容探测，别按后缀
- 单元素复用还顺手解决了 iOS 自动播放限制：用户手势 `play()` 过一次的元素，换 `src` 后程序化 `play()` 仍被允许
- 别走"Web Audio 全解码两轨再同步"的路：sample 级同步是准了，但 `AudioBufferSourceNode.playbackRate` 改变音高，练歌必需的 0.5x/0.75x 变速就没了；HTMLAudio 的 `playbackRate` 自带保音高

## 适用范围

- 适用于：多轨可开关的网页播放器，手机 / 微信内嵌是主要场景；轨道组合有限（几种）可穷举预混
- 不适用于：轨道很多且组合爆炸（DAW 类）；需要用户实时连续调各轨音量；内容每天变动预混跟不上
