# 反模式：测试全绿，但把修复拆掉它还是全绿

> 来源：贸易数据 MCP 分页丢记录修复（2026-08-18/19）
> 结果：一轮修复里出现 **4 种**不同形态的假守卫，其中 2 种是独立评审抓出来的

## 一句话结论

写完守卫要做一步反向验证：**把修复拆掉，跑这条测试，它必须转红**。没红就说明它守的不是你以为的东西。这一步花不了两分钟，但它是"测试存在"与"测试有效"之间唯一的分界线——而这两者在 CI 的绿勾里长得一模一样。

## 场景

- 修一个**机制性缺陷**（并发、分页、缓存失效、分片、时序），缺陷的触发依赖特定数据形态
- 测试用的 fixture 是随手挑的"有代表性的真实数据"
- 测试直连底层（数据库 / HTTP API）验证"底层语义"，而不是走产品代码路径
- LLM 写的测试：它会忠实地把断言写出来，但不会主动怀疑这条断言是否可达

## 踩坑经历

一次 ES 分页缺陷（`search_after` 配 `_doc` 排序，多分片时页边界丢记录）的修复中，四条守卫全是假的：

**① fixture 触发不了缺陷。** 集成测试"翻到底必须等于总数"跑的是墨西哥 2026 索引——单分片。缺陷只在多分片上出现，所以修不修都绿。
→ 补了一个**对照组**：直接用旧实现打同一个 fixture，断言它**确实翻不全**。这条对照组本身就是"fixture 是否有判别力"的守卫，fixture 哪天失效了它会先红。

**② 守卫绕过了产品代码。** 新加的多分片用例是自己拼 ES 请求、硬编码排序字段，验证的是"ES 加了 tiebreaker 就不丢记录"——这是 ES 的语义，不是我们的接线。把产品代码里 `tiebreaker=_tiebreaker` 改成 `tiebreaker=None`，整个分页测试套件依然全绿。
→ 补了一条走完整产品栈（能力快照 → 查询参数 → 排序）的端到端用例，**并真的拆掉接线确认它转红**。

**③ 断言的分支根本到不了。** 一条单测断言"没有可用索引时不应发出某告警"，但产品代码在更上游就 early-return 了，永远走不到被测分支。改不改代码它都通过。
→ 删掉。同时把源码里"空集 = 没有可查索引"的注释一并改掉——那句注释是给自己讲的故事，不是代码事实。

**④ xfail 修好后没转红。** 用 `xfail(strict=True)` 标记已知缺陷，本意是"修好后自动转红提醒删除"。但这条测试构造参数时没带上修复引入的新字段，所以走的仍是降级路径，修好后依然 xfail。
→ 改成正向守卫，并保留一条对照断言：不带 tiebreaker 时**确实**会丢记录（把降级路径的代价也钉住）。

## 数据支撑

决定性 fixture（`ve_01_exp_index_2020_v1`，5 分片 / 4769 条，match_all 翻到底）：

| 排序键 | 翻到底拿到 |
|---|---|
| 仅 `_doc` | 4768（稳定少 1） |
| `_doc` + 业务主键 | 4769 ✅ |

同一个缺陷，换成稀疏过滤查询跨 3 个单分片索引（21642 条）：两种排序**都不丢**。所以"我试了一下没问题"完全不能作数——触发概率取决于命中密度，`match_all` 让每个页边界都落在并列组里必丢，稀疏查询碰撞概率极低。

这也解释了为什么最初的 fixture 是假守卫：它恰好落在不触发的那一侧。

## 做法

守卫写完后按顺序自问四句，任何一句答不上来就别提交：

1. **把修复拆掉，它红吗？** —— 真去拆，别推理。这是唯一不能省的一步。
2. **它打在产品代码路径上吗？** —— 直连底层验证的是底层语义。底层语义本来就是对的，你修的是自己的接线。
3. **被断言的分支可达吗？** —— 上游有没有 early-return / 短路 / 异常吞掉，让这段成了死代码。
4. **fixture 能触发缺陷吗？** —— 机制性缺陷对数据形态敏感。挑 fixture 要按"什么形态必然触发"来选，不是按"什么数据看着典型"。

对第 1 条，最省事的做法是留一个**对照组用例**常驻：断言旧实现在这个 fixture 上确实失败。它把"拆掉修复试一次"这个一次性动作变成了持续守卫——fixture 哪天因数据变化失效，对照组会先红，而不是等真出事。

## 适用范围

- 适用于：机制性缺陷的回归守卫，尤其是并发 / 分页 / 分片 / 缓存 / 时序这类"依赖特定数据形态才触发"的
- 适用于：让 LLM 写测试的场景——它写断言很可靠，怀疑断言可达性不可靠，这一步得由人或独立评审补
- 不适用于：纯函数的输入输出测试（断言不可达是显式的，一眼能看出来）
