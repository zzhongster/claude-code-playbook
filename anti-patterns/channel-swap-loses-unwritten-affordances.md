# 换渲染通道时，旧通道免费给的行为不在任何改动清单上

> 来源：TOUCH 2.0 企微群机器人（2026-08-14，TOU-345 / TOU-347）

## 一句话结论

替换一个实现时，被替换的那个特性一定会被测；**旧实现「附赠」的、没人写下来因而也没人保护的行为不会**。换通道前要问的不是「新的能不能做到我要的」，而是「**旧的在替我做什么我没意识到的事**」。

## 现象

群机器人的消息发送从 `msgtype:"text"` 换成 `markdown`，动机很干净：让 @ 能内联放在首行（`mentioned_list` 的 @ 被平台固定追加在消息末尾，位置改不了，于是正文开头再手写一个 @ 就成了一头一尾两个、开头那个还点不动）。

换完当天，一条带 Linear 链接的通知发出去，**链接点不动**。

三写法对照（同一条消息一次发出，人肉眼确认）：

| 写法 | 结果 |
|---|---|
| 裸 URL `https://...` | **不可点** |
| `[文字](url)` | 可点 |
| `<font color="comment">[文字](url)</font>` | **也可点** |

第三行是为了排除另一个候选原因（那条消息的链接呈灰色，怀疑是灰字标签吃掉了语法）——结果 `<font>` 只染色、不吃链接语法。**裸 URL 是唯一的因。**

## 根因

`text` 模式下**客户端会自动把裸 URL 渲染成可点链接**，`markdown` 模式不做这件事。而这个便利：

- 不在我们的代码里（是客户端行为）；
- 不在任何文档里；
- 没有任何测试依赖它。

三个「不在」加起来，它就不可能出现在改动清单上——直到它消失。

**换通道那次的验收是扎实的**：三条对照实测、发进真实群、人肉眼确认。问题在于三条**全部在验 @**：覆盖了改动点，没覆盖使用场景。而发链接恰恰是这个命令最常干的事（团队规约还专门要求「群里贴一行链接，不复述内容」）。

失败是静默的：接口返回 `errcode==0`、消息正常送达、格式看着没毛病，唯独链接点不动——不点它就不知道。

## 正确做法

1. **换通道 / 格式 / 库 / 协议前，单列一张「旧实现免费给了什么」的清单逐条核**：自动链接、自动换行、转义、长度上限、富文本、字符编码、默认超时。逐条问「新通道还给不给」；
2. **验收用例必须包含一条「典型完整产物」，不能只测被改的那个元素。** 真实产物长什么样，用例就该长什么样——本次三条对照全不带链接，是「测了改动点、没测使用场景」的标准形态；
3. **渲染类结论只能人眼确认。** `errcode==0` 证明的是「对方收下了」，不是「渲染对了」。凡是「发出去给人看」的东西，验收的最后一步必须有人真的看一眼；
4. 定因用**排除性实验**而不是解释性推断：本次一条消息里并排三种写法，一次把「不可点」和「变灰」两个候选原因分开——比逐个猜快，也比只有一个样本可靠。

## 更一般的教训

**「我改的那件事」和「我顺带弄坏的那件事」不在同一个视野里，而验证天然只覆盖前者。**

这类缺陷有个共同的形状：**没人声明依赖的行为，也就没人保护**。它不像 API 破坏那样有编译期或类型系统兜着，它在运行时静默降级成「看起来正常，只是少了点什么」。

## 适用范围

- **适用于**：换消息通道、换渲染器、换序列化格式、换 HTTP 客户端、换模板引擎、换 Markdown 解析器——任何「看起来只是换个写法」的替换；
- **不适用于**：纯新增功能（没有旧实现的附赠可丢）。
