# 反模式：多来源合并时，让一个来源的验证结论覆盖另一个

## 一句话结论

同一条数据从两个来源拿到、各带一个验证结论时（A 说有效、B 说无效），合并逻辑里一句「按 B 重新打标」就会**悄悄删掉 A 的结论**，下游再按「无效不列」过滤，数据就消失了——没有报错，只有用户看截图时问一句「为什么没有邮箱？」。**两个结论分开存，冲突单独标出来，由规则或人决定，不能让后处理的那个默认胜出。**

## 场景

- 联系人邮箱：数据库自带「有效」标记 + 第三方独立验证结果
- 公司信息：企业库值 + 官网/工商值
- 任何「去重合并后再统一打标」的管线：合并时把 `src` 拼成 `"A+B"`，后面的判断却还在比 `src == "A"`

## 踩坑经历（2026-10-19）

一个联系人的邮箱，联系人库返回并标「有效」，原表里也有同一个邮箱。去重时两条合成一条，来源拼成 `"联系人库+原表"`。后续给邮箱打验证标签的循环：

```python
if e["src"] == "联系人库": continue      # 联系人库的保留自带标记
e["check"] = snov_label(e["email"])     # 其余按独立验证打标
```

合并后的 `src` 不再等于 `"联系人库"`，于是被独立验证的「无效」覆盖；出表时「独立验证无效的不列」——**一个数据源判有效的邮箱从交付表里消失了**。用户看截图发现「这个人一堆电话却没有邮箱」才暴露。

同一次排查还牵出统计口径的偏差：合并来源的邮箱原本都被归到了「独立验证有效」，修正后「数据源验证有效」从 21 变 32、「独立验证有效」从 28 变 17——总数不变，但之前的分项统计是错的。

## 怎么做

1. **每个来源的结论各占一个字段**：`check_source`、`check_independent`，不要共用一个 `check` 让后写的覆盖先写的
2. **冲突显式化**：两个结论不一致时标「存疑」，保留数据并写明原因，不按其中一方直接过滤
3. **合并来源后的判断用「包含」不用「等于」**：`"联系人库" in src`，或者干脆用来源集合
4. **过滤规则只作用于「确定无效」**：至少一方说有效、另一方说无效 ≠ 确定无效
