# 反模式：指标是绿的，但它绿的原因不是你以为的那个

## 一句话结论

验收时挑的那个指标，可能在**故障最严重的时候恰好返回正常值**——因为故障本身消解了它测量的那个量。查布局溢出用 `scrollWidth > clientWidth` 就是典型：文字被挤爆后会纵向坍缩，横向溢出被吸收掉，于是"没有溢出"，而页面已经不能看了。选指标时要问的不是"它能不能反映问题"，而是"**故障发生时它会变成什么**"。

## 场景

- 用一个聚合量/边界量代理一个结构性问题（用溢出代理布局崩坏、用退出码代理任务成功、用行数代理内容完整）
- 故障模式恰好会让被测量的那个量回到正常范围
- 自动化验收只看这一个数

## 踩坑经历

视频剪辑工具 cutmap 二期（2026-08-03）。页面重做后要验证响应式，实现者的自查是：

```js
document.body.scrollWidth > document.body.clientWidth  // → false，无横向溢出 ✅
```

430px（手机）视口下这个值确实是 `false`。但页面实际长这样：卡片里的说明文字被三个 `nowrap` 的兄弟元素挤成 `width: 0`，中文没有天然断行点，于是**逐字竖排**，一张卡片的高度从正常的 80px 撑到 483–806px，8 张卡片全中招。

指标为什么是绿的：**文字纵向坍缩把横向溢出吃掉了**。溢出没有发生，恰恰是因为破版已经足够严重——元素宁可长到 800px 高，也不横着出去。指标在最该报警的时候失灵。

换成量元素实际高度，问题立刻现形：

| 视口 | 修复前 `.card` 高度 | 修复后 |
|---|---|---|
| 430 | 483 / 691 / 599 / 806 / 737 / 806 / 483 / 806 | 91 / 114 / 114 / 114 / … |
| 768 | 44–67 | 44–67（无变化） |
| 1280 | 44 | 44（无变化） |

**同一次修复里，根因分析也差点栽在类似的地方**：直觉答案是"缺 `flex-wrap: wrap`"。加上之后 430px 的高度从 806 降到 438——好了一半，看起来像修好了。实际上 `.grow` 写的是 `flex: 1`，展开是 `1 1 0%`，**basis 为 0 意味着这个元素永远"放得下"，换行条件根本不会触发**。必须同时把 basis 改成一个非零值（`flex: 1 1 14rem`）才真正解决。用"改了之后变好了"当验证标准，会停在半路。

## 解法

1. **选指标时做一次"故障态推演"**：假设故障已经发生到最严重，这个指标会是多少？如果答案是"正常范围"，换指标。
2. **量结构，别量边界**：布局问题量元素的实际几何（高度、宽度、位置），不要量容器的溢出标志。前者在故障时必然异常，后者可能被吸收。
3. **验证修复时用"改坏再验红"**：把修复代码临时改回去（或改成半吊子版本），确认指标真的会变红。半吊子版本尤其重要——它能区分"真修好了"和"改善了但没解决"。
4. **对照组要覆盖没问题的档位**：上面那张表里 768/1280 两档修复前后**数字完全一致**，这条信息和 430 档的改善同样重要——它证明修复没有破坏原本正常的场景。

## 教训

- "这个指标是绿的"和"这件事没问题"之间隔着一个假设：**指标与故障是单调相关的**。这个假设经常不成立，而且恰恰在故障严重时最不成立。
- 一个能给出虚假绿灯的验证，比没有验证更危险——它会终止调查。实现者跑了这个检查、拿到 `false`、写进报告"430px 无横向溢出"，整件事就此结案，直到审查者去量了高度。
- 这类问题在 AI 流水线里更容易发生：subagent 倾向于挑一个"看起来在测这件事"的现成 API，而不是先想清楚故障态长什么样。任务书里与其写"验证响应式"，不如写"在 430px 下量每张卡片的高度并报出来"。
