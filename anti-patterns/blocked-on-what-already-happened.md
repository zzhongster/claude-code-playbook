# 反模式：报「卡在别人那儿」之前不回查——「没有回音」有三种含义，而它们体验完全相同

## 一句话结论

**「我提了但没人理」是感受，不是观测。** 沉默至少有三义：**已经处理了**（通知没看到、没回查）、**不需要处理**（这条路径本来就不需要对方）、**真的没人处理**。三者在报告者这一侧长得一模一样——都是「我发出去了，然后什么都没发生」——而正确处置完全相反（去合 / 自己动手 / 才是去催）。报阻塞之前，先花一次 API 调用回查那件事的当前状态。

推论：**阻塞清单是所有清单里最该被回查的一种**，因为它天然只由报告者单侧的信息构成。

## 场景

- 多人协作 + 异步审批：提了 PR / 申请 / 问题，然后等
- 决策与执行分散在不同载体：裁决记在 A 卡，执行卡是 B，B 上没有 A 的**状态**
- 通知不可靠：群消息刷过去、邮件淹了、平台通知没开——**沉默不是信号，是缺省**
- AI agent 汇总待办：把用户口述的「在等 X」照单转成待办，不做状态核实

## 踩坑经历

TOUCH 2.0，2026-08-12。一位同事发来一份清单，五件事声称卡在决策者这儿。逐条核实后**只有一件成立**：

| 报的 | 实况 | 沉默属于哪一义 |
|---|---|---|
| PR A「CI 全绿，就等人看」 | 决策者 20:15 已批准，可合状态 CLEAN | 已处理 |
| PR B「也在等」 | 19:52 已批准（批准晚于末次 commit，未被 push 作废） | 已处理 |
| PR C「也在等」 | 改的路径在受管表**之外**，零批准，自己合即可 | 不需要处理 |
| 「判据 X 要你拍板」 | 前一天已裁，结论逐字写在另一张卡上 | 已处理 |
| 「判据 Y 要你拍板」 | ✅ 唯一真待办 | 真没人处理 |

而**他真正被卡住的地方没有出现在清单上**：他自己两条 PR 的 CI 是红的，其中一条正是下游那个「硬前置」的承载物。阻塞在自己手上，不会以「有人欠我」的形式出现，所以不进清单。

### 第二层：内容转述了，状态没转述

那条「判据 X 要你拍板」值得单独看。承接卡上**其实抄了裁决的技术内容**（点名了要走哪套函数），但没写「**这是已裁事项**」。读的人看到一段技术要求，判断不出它是**已定结论**还是**候选方案**——在安全敏感的改动上，读不出状态就默认停下来等确认。于是一个早就做完的决定，让下游停了几天。

**转述一个决定时，「这是个决定」和「决定的内容」要一起转述；只转内容会被读成提议。**

### 第三层：同一枚硬币的反面，当天我自己踩了

给这个坑写反例库条目时，我把分支命名为 `t2-<卡号>-<简述>`，PR 标题也带了卡号，但正文里既没写 `Closes` 也没写 `Part of`。合并时自动化按默认路径把那张卡标成了 **Done**——而那张卡三条判据只做了一条，另两条是安全项（几张认证表还没开行级安全）。铁证是时间戳差 2 秒：

```
卡 completedAt   13:33:31Z
PR  mergedAt     13:33:29Z
```

**报「已完成」和报「未完成」是同一个失效模式的两面**：状态信号靠巧合（命名相似）而非显式声明传播，就必然有时对、有时错，且错的时候没有任何东西会响。更难堪的是，这个坑在该项目的反例库里**已经有条目**（「裁决卡 Done 了、实现那一半没人接」），我是在给它写新条目的那次提交里又踩了一遍。

## 正确做法

1. **报阻塞前回查一次状态。** 成本是一次 API 调用，收益是不把已完成的事重复推一遍：

   ```bash
   gh pr view <n> --json state,mergedAt,reviews,mergeStateStatus
   ```

   ⚠️ 两个易错点：`reviewDecision` 为空**不等于**没人批（要看 `reviews[]` 数组本身）；批准是否仍有效要**比对批准时间与末次 commit 时间**（多数仓库开了 push 作废旧批准）。

2. **等批准之前先对一次权限/流程表。** 「需不需要对方」和「对方做没做」是两个问题，多数人只问后者。**等一个不需要的批准比没人批更浪费——它永远等不到。**

3. **转述决定时带上状态标签。** 写「**已裁（日期 · 见 X 卡 Y 段）**：<内容>」，而不是只把技术要求抄一遍。同理，写「待裁」的注释要能被回查到卡号。

4. **完成信号必须显式，不能靠命名巧合。** 自动化按分支名 / 标题里的标识符关联工单是常态，但**关联 ≠ 完成**。用平台约定的显式关键词区分（如 `Closes` vs `Part of`），并且：**只是"提及"某工单的 PR，不要用那个工单号命名分支。**

5. **自查清单里加一条反向问题**：「我列的这些'在等别人'，有几件其实在等我自己？」本例中真正的关键路径全在报告者自己手上。
