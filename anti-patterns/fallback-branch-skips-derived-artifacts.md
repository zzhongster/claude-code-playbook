# 反模式：构建脚本的容错分支不产出派生文件——与接口无关的内容被连累到根本不生成页面

## 一句话结论

前置脚本抓远端内容失败时"沿用旧快照"看着很稳妥，但那条分支**同时跳过了 sitemap 与预渲染清单的重算**。于是另一份与那个接口毫无关系的**本地**内容既不进 sitemap，也不进预渲染 include 清单——后者意味着那些页面**根本不产出静态文件**，爬虫拿到的是 SPA 空壳。**降级的边界应该是"哪些输入拿不到"，不是"哪一步跳过"**：容错分支必须和成功分支产出同一组派生文件。另外，本地内容源的错误应当**硬失败**，只有远端抖动才容错——两类错误不要共用一个 catch。

## 场景

- 构建前置脚本（prebuild）既抓远端内容，又据此重算派生产物：sitemap、预渲染路由清单、搜索索引、RSS、`robots.txt`
- 派生产物的输入**不止**远端那一份，还包含仓内本地内容（Markdown / JSON 文章、静态路由表）
- 远端挂了 / 限流 / 网络抖动时脚本"优雅降级"，不让构建失败

## 详细说明

### 原来的失败路径

```js
try {
  news = await fetchNews(origin);
  writeSnapshot(news);
  rebuildSitemap(news, localArticles);        // ← 只在成功路径上
  rebuildPrerenderInclude(news, localArticles); // ← 只在成功路径上
} catch (e) {
  console.warn('新闻接口抓取失败，沿用旧快照');
  return;                                      // ← 派生产物一个都没动
}
```

**后果分级，而且差一个数量级：**

| 漏掉的派生产物 | 后果 |
|---|---|
| sitemap 少一条 | 慢一点被发现、重抓优先级低——可恢复，损失是时间 |
| **预渲染 include 清单少一条** | **这一页根本没有静态 HTML**。SPA 下爬虫看到的是空壳，页面等于不存在 |

同一条 `return` 造成这两种后果。而触发它的是**另一个系统**的抖动——新加的本地文章和那个新闻接口毫无关系，却被它连坐。

### 改法：降级只降输入，不降步骤

```js
let news;
try {
  news = await fetchNews(origin);
  writeSnapshot(news);
} catch (e) {
  console.warn('新闻接口抓取失败，沿用旧快照的新闻索引');
  news = readSnapshot() ?? [];        // 无历史快照时用空索引，同样往下走
}
// 派生产物在分支外重算：远端那部分可能是旧的，本地那部分永远是当前的
rebuildSitemap(news, localArticles);
rebuildPrerenderInclude(news, localArticles);
```

一句话：**远端拿不到就用旧的那一份远端数据，其余输入照常参与重算。**

### 第二半：本地源 fail loud，远端源 fail soft

同一个脚本里两类错误的正确行为是相反的：

- **远端**（接口、CDN、第三方）——抖动是常态，容错，用旧数据，构建继续
- **本地**（仓内 JSON/Markdown）——坏了就是有人写错了，**当场退出码 1**：JSON 不合法、slug 与文件名不符、缺必填字段、日期格式错。宁可构建失败，也不要静默发一个坏页

这两类**不要共用一个 `catch`**。共用的那一刻，"我写错了一个逗号"就继承了"上游挂了"的全套语义——于是本地内容的错误被当成远端抖动，容错掉了。

### 怎么测容错分支：真跑，别读代码

指向一个**不可达 origin**，这是最省事的注入点：

```bash
# 9 是 discard 端口，立即拒连，不用 mock、不用改代码
NEWS_SNAPSHOT_ORIGIN=http://127.0.0.1:9 npm run build

# 断言：远端失败了，但本地内容仍然进了两份派生产物
grep -c '/insights/' build/sitemap.xml                 # 必须 == 本地文章数（列表页是 /insights，不带尾斜杠，不在此计数内）
ls -d build/insights/*/index.html | wc -l              # 必须 == 本地文章数
```

无历史快照的那条分支同理：把快照文件临时移走再跑一遍。**两条失败路径都要跑**——它们是不同的代码。

## 怎么防

1. **列出脚本的全部派生产物，对每条分支逐一断言产出**：成功 / 远端失败 / 无历史数据，三条路径一张表。
2. **派生清单加条数下界断言**：`预渲染清单条数 < 本地内容条数` 直接 die。清单类产物最危险的失效形态是"少了几条"，而不是"空了"。
3. **本地源与远端源分开 catch**，错误文案可区分（下游和人都要能分流）。
4. **容错分支的测试必须真跑**，不可达 origin / 临时改名文件是零成本的故障注入。

## 数据支撑

- 这一条是在**造成事故之前**被发现的：新增的本地内容与这个缺陷同一次构建相遇，所以没有线上损失数字。但失败分支的行为是实测的——`NEWS_SNAPSHOT_ORIGIN=http://127.0.0.1:9` 下两条路径都跑过，修复后本地内容照常进 sitemap（50 条）与预渲染清单（52/52 页面产出）。
- 同项目早一步的对照事实：一次预渲染改造做完后**从未部署**，线上首页四个月一直是 649 字节的 SPA 空壳，没有任何人发现（见「相关」）。**"页面没产出"这类缺陷的自然发现周期以月计**，所以它必须靠构建期断言拦，而不是靠人察觉。

## 适用范围

- **适用于**：任何"抓取 + 据此重算派生产物"的构建前置脚本；sitemap / 预渲染清单 / 搜索索引 / RSS / OpenAPI 聚合 / i18n 词条合并
- **推广形态**：凡是一个 `catch` 同时覆盖"外部不可控"和"自己写错了"两类条件，降级语义就会被后者冒用
- **不适用于**：派生产物的输入只有那一个远端源（没有本地内容会被连坐；但"少了几条"的断言仍然值得加）
