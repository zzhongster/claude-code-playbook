# 反模式：组织树权限校验用扁平表精确匹配，漏判全部子部门成员

## 一句话结论

判断"用户是否属于某个部门/标签范围"时，如果 API 只返回用户**直接挂载**的部门 id（不含祖先链），拿它去跟"授权范围部门 id 集合"做精确匹配（`&` 交集），会漏判所有挂在**子部门**下的人——只有"直接挂在范围部门本级、不在任何子分组下"的极少数人能通过。这类 bug 用管理员/测试账号验证不出来（管理员账号往往走角色直通），只有真实末端用户测试才会暴露，而末端用户往往正是这种组织架构里人数最多的那一层。

## 场景

- 企业通讯录 / RBAC 系统里，组织结构是多级树（部门→分公司→小组），业务范围授权挂在某个中间层级的部门上，语义上"挂了这个部门 = 该部门 + 所有子部门都算数"
- 权限判断代码里，判断"用户属于哪个部门"的字段（例如企业微信 `user/get` 返回的 `department`）只给出用户**直接挂载**的叶子部门 id，不包含从叶子到根的完整祖先链
- 权限校验逻辑直接拿"范围部门 id 集合"跟"用户部门 id"做交集判断，没有做树展开

## 踩坑经历

trade-ai 销售线索库（2026-08-18，Issue #401）。功能刚上线时用管理员/superadmin 账号验证一切正常，真正邀请一线销售实测时，几乎全员收到"不在可见范围内"的 403。

排查发现企业微信通讯录结构是三级：`销售部(8) → 杭州分公司(9) → 杭州三组(31)`，真实销售全部挂在第三级（如"杭州三组"）下。系统里用企微"标签挂部门"做范围控制，标签的 `partylist` 只挂了顶层 `销售部(8)`。判断逻辑是：

```python
party_ids = set(data.get("partylist") or [])   # {8}
user_data = await _qyapi_get("user/get", {...})
if party_ids & set(user_data.get("department") or []):   # 用户 department 是 [31]，不是 [8]
    return True
```

`{8} & {31}` 永远不命中——**只有直接挂在"销售部"本级、不在任何三级子部门下的极少数人能通过**，真正的一线销售（分布在各个"XX 组"子部门）全部被判定成不在范围内。这个 bug 是代码上线时就存在的，一直没暴露，因为验证的人（管理员）走的是角色直通逻辑，根本没跑到这段部门匹配代码。

同一个函数里还挖出第二个独立 bug，根源是同一类"没验证 API 真实返回结构"：企微 `tag/get` 接口的 `userlist` 字段实际是**对象列表**（`[{'userid':..., 'name':...}]`），代码却拿字符串直接判断 `wecom_userid in userlist`——类型完全不对，这个判断分支从创建以来恒为 `False`，等价于死代码，但因为多数人是靠部门覆盖命中的（哪怕命中方式本身也是错的），这条路径的失效长期没人发现。

## 根因

两条 bug 共享同一个更底层的教训：**代码作者假设"某个官方语义"（标签挂部门=子部门全覆盖）已经被自己写的匹配逻辑正确实现，但从未对着 API 的真实返回结构验证过这个假设**。

- 树形归属关系的"从属"判断，只有在字段本身返回**完整祖先链**或调用方主动做**树展开**时，精确匹配才等价于"属于"。多数通讯录/组织架构类 API（企业微信、飞书、AD/LDAP 等）出于性能考虑只返回直接挂载的叶子节点，这是常态而非例外。
- 静默类型不匹配（字符串 vs 对象列表）在动态类型语言里不会报错，只会让判断结果恒为某个固定值——这种 bug 尤其危险，因为它"看起来在工作"（不抛异常、不 500），只是悄悄地从不为真。

## 解法

1. **树形归属判断前先展开子树**：拉一次组织结构的扁平列表，建 `parentid → children` 映射，对"范围根节点集合"做 BFS/DFS 展开成"自己+全部子孙"的完整集合，再跟用户的直属节点做交集。组织结构变动频率通常远低于成员变动，这个展开结果可以用比"成员范围判断结果"更长的 TTL 单独缓存。
2. **不要相信字段名暗示的类型，去读一次真实返回值**：写权限判断这类"一旦想当然就会长期潜伏"的代码之前，实际调一次 API 打印真实响应，确认字段是字符串列表还是对象列表、是否含祖先链，而不是照着接口文档的自然语言描述去猜结构。
3. **写测试时构造真实的多级树场景**，不要只测"直接挂在根节点"这种最简单情形——这种简单情形恰恰是本来就会通过的少数人，掩盖不了子树展开缺失的问题。

## 验证方法

怀疑"权限范围判断有漏判"时：

1. **不要只用管理员/测试账号验证**——这类账号大概率有角色直通之类的旁路，永远走不到真实的范围判断逻辑
2. 找一个组织架构里**末端、非管理层**的真实账号（这类角色人数最多，也最容易踩中"挂在子部门"的场景），直接手动调用范围判断函数（绕开缓存）看结果
3. 打印判断逻辑依赖的每个字段的真实返回值和类型，逐项核对是否符合代码里的假设（是不是对象列表当字符串列表用了、是不是精确匹配当树形归属用了）

## 适用范围

- **适用于**：任何"组织树 + 挂节点做范围控制"的场景——企业微信/飞书通讯录标签、AD/LDAP 组、RBAC 里挂在部门/组织单元上的角色，只要判断逻辑用的是"用户直属节点 id 精确匹配范围节点 id 集合"
- **不影响**：范围直接挂在叶子节点本身（没有多级树）、或 API 本身就返回包含祖先链的展开列表的场景
- **提前预防**：设计任何"挂在组织树节点上做范围/权限控制"的功能时，实现阶段就该把"树展开"当成必选项去写，而不是等真实多级场景暴露漏洞后再补
