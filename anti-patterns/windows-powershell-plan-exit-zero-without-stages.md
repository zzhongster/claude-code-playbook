# 反模式：PowerShell 自动化只看退出码，把“没有执行计划”当成成功

## 一句话结论

Windows PowerShell 5.1 自动化中的 `exit 0` 只能证明脚本进程没有显式失败，不能证明计划被正确解析、逐阶段执行或完成清理。编码误读、数组序列化和计划文件行数异常，都可能让执行器没有跑到目标阶段，却仍被上层包装成“成功”。

## 实测事故链

一次遗留 Windows 客户端的只读校准共进行了四次独立运行：

1. 第一次运行使用 UTF-8 无 BOM 脚本并包含中文字符串，在 Windows PowerShell 5.1 下发生解析失败。客户端未启动，业务数据变化为 0。
2. 第二、三次运行修复编码后，计划对象被意外序列化成一行。执行包装器返回成功，但预期阶段文件不存在；新增的“阶段必须齐全”闸门识别出假成功。两次运行的业务数据变化仍为 0。
3. 第四次运行改用纯 ASCII 脚本正文构造非 ASCII 标题，以 `List[string].Add()` 逐行建立计划，再用 `WriteAllLines()` 落盘，并在包装器结束后核对每个阶段文件。最终 12 个阶段中 9 个通过、3 个因安全协议限制而明确标记为不支持；业务数据变化 0、临时对象残留 0、数据库一致性检查通过、完整性清单不匹配 0。

这说明“进程成功”“执行器成功”“阶段成功”“系统恢复原状”是四个不同命题。

## 根因

- Windows PowerShell 5.1 会按本地 ANSI 代码页读取无 BOM 的脚本，非 ASCII 内容可能破坏语法。编码细节另见 [ps51-utf8-no-bom-gbk-mangles-chinese.md](ps51-utf8-no-bom-gbk-mangles-chinese.md)。
- PowerShell 的数组、管道和隐式字符串转换具有上下文相关行为。看起来是多条命令的对象，写入文件后可能只剩一条逻辑行。
- 上层控制器只消费子进程退出码，没有核对期望阶段、产物结构和最终状态。
- 执行日志中的“完成”来自自动化自身，缺少独立证据，无法排除空跑或提前退出。

## 防护模式

### 1. 先固定脚本编码契约

- 给 Windows PowerShell 5.1 的脚本使用 ASCII 正文或 UTF-8 BOM。
- 必须匹配非 ASCII 窗口标题时，在运行期用 Unicode 码点构造，避免源文件编码参与解析。
- 在目标 Windows 版本上先执行语法解析，再进入业务运行。

### 2. 计划必须有结构闸门

- 使用强类型 `List[string]` 和显式 `.Add()` 建立命令列表。
- 使用 `WriteAllLines()` 写入，不依赖隐式数组转字符串或通用 `-join`。
- 执行前核对计划行数、阶段 ID 的唯一性和必需阶段集合。
- 执行后核对每个预期阶段产物；缺一项就失败，即使子进程退出码为 0。

### 3. 不信任同一执行器的自证

最终成功必须同时满足：

- 预期阶段全部有明确结果：通过、失败或协议不支持；
- 业务数据指纹前后一致，允许的系统级变化单独列出；
- 临时进程、任务和对象残留为 0；
- 数据库一致性检查通过；
- 完整性清单逐文件匹配；
- 独立验证器在执行器结束后重新读取现场并得出同一结论。

### 4. 每次运行使用不可变目录

- 每次尝试写入新的运行目录，不覆盖失败运行。
- 失败现场保留到根因确认和最终成功之后。
- 仓库只保存脱敏摘要、相对证据路径与哈希；不保存服务器标识、地址、用户名、凭据、绝对路径、原始日志或截图。

## 适用范围

该模式不只适用于桌面 UI 自动化，也适用于安装器、迁移脚本、批处理、计划任务、远程运维和任何“脚本退出码代表业务完成”的流水线。
