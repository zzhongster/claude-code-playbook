# 反模式：证据与失败态长得一模一样——零判别力的「证据链」

## 一句话结论

下结论前问一句：**「有没有一种它没跑/没生效的情形，也会长成现在这样？」** 答得上来，手里的就不是证据，是与结论恰好兼容的观测。三条这样的观测叠在一起也不会变成证据——零乘三还是零。配套的第二问：你验的是「**存在**」还是「**有效**」？配置在、变量在、文件在，都只是存在；只有拿它真调一次目标系统并看响应，才是有效。

## 场景

- 从**产物痕迹**反推**流程执行**：看到构建产物有某工具的注入标记/清理痕迹，推断「上传/发布/同步那一步跑过了」
- 从**配置存在**反推**配置生效**：面板里显示已配、环境变量非空、条件展开通过，推断「凭据没问题」
- 失败路径是**静默**的：告警被 silent/log-level/重定向吞掉，失败与成功在所有你看得到的地方同形

## 踩坑经历

TOUCH 2.0 验证 Sentry source map 上传（2026-08-08）。给出过一条三证齐全的「已生效」结论：

1. 线上 chunk 带 `_sentryDebugId` 注入标记；
2. `sourceMappingURL` 全被剥掉、`.map` 公网 404（配置里 `deleteSourcemapsAfterUpload: true`）；
3. sentry-cli 二进制在、`NEXT_PUBLIC_*` 变量能内联（证明构建期读得到环境变量）。

结论被同事逐行核源码推翻：`@sentry/bundler-plugin-core` 的四步里**只有 createRelease 和 upload 在 token 门后面**，注入 debug ID 和删 `.map` 无门槛照跑——`deleteSourcemapsAfterUpload` 的「AfterUpload」只是函数名，它不检查上传发生过没有。所以**无 token 静默跳过的产物与上传成功的产物指纹完全相同**，三条证据判别力全为零。

真相第二天翻出来更难看：Zeabur 上那枚 `SENTRY_AUTH_TOKEN` 是**63 位**（应为 64 位十六进制，人工粘贴丢了字符），Sentry 判 `Invalid token`。全链路四层检查——平台面板「已配」、代码条件展开 `process.env.X ?`、插件门 `!options.authToken`、人工核对「三个变量都在」——**全部在验存在，没有一层验有效**；唯一会说「无效」的 401 告警被 `silent: !process.env.CI` 消音（构建不在 CI 里跑）。坏 token 零症状运行了一整天。

## 正确做法

1. **判别力自检**：对每条「证据」问「它没跑也会这样吗」。回答依据必须来自**源码或实测**，不是文档或直觉——推翻上面结论的方法就是去 `node_modules` 里核那四步各在哪道门后面。
2. **选判别位**：找**与目标动作共用同一道门、且更早/更便宜可查**的观测量。本例是 release：createRelease 与 upload 共用 token 门且跑在最前，「Sentry 里 release `<SHA>` 在不在」一个 GET 定案。
3. **凭据验收必须真调一次**：长度/格式先校（粘贴后即时自检），然后拿它对目标 API 发一个最小请求看响应码。**零转录实测**能同时排除「抄错了」：在目标运行环境内直接用它自己的环境变量发请求（如 `zeabur execute-command` 容器内 `curl -H "Authorization: Bearer $SENTRY_AUTH_TOKEN" …`），值不经过任何人手。
4. **存在 / 被读到 / 有效，三件事三道验法**：存在断言（CI 里断言变量名在、旧名不在）防的是命名漂移；「被读到」要差分验（改值、看行为跟着变）；「有效」要真调。谁也替不了谁，报告里写清验的是哪一层。
