# 反模式：单测里新旧代码不共存，所以测不到"部署那一刻"

> 来源：贸易数据 MCP 分页游标改造（2026-08-19）
> 结果：单测 626 全绿、集成全绿、黑盒全绿，仍有一个部署瞬间必然触发的 Blocker，靠独立评审抓出来

## 一句话结论

只要有**客户端持有、跨请求回传**的状态（分页游标、续传 token、序列化载荷、缓存键），改它的格式就等于让**新旧两版代码通过这份状态通信**。而单测进程里只有一份代码，结构上就不可能覆盖这种通信。要测它只有一个办法：**手工构造上一版格式的状态，喂给新版代码，断言它不炸**。

## 场景

- 改动涉及：分页游标 / 恢复 token / 断点续传位置 / 序列化的请求上下文 / 带版本语义的缓存键
- 这份状态由调用方持有，可能隔几分钟、几小时才回传（LLM 会话尤其如此——用户去干别的了，回来接着翻页）
- 灰度或滚动发布期间，同一份状态可能在新旧实例之间来回

## 踩坑经历

给 ES 分页加去重排序键，排序字段从 1 个变成 2 个。ES 的硬性约束是 **`search_after` 的长度必须恰好等于 sort 字段数**：

```
sort 2 字段 + 游标 1 值 → 400  "search_after has 1 value(s) but sort has 2"
sort 1 字段 + 游标 2 值 → 400  "search_after has 2 value(s) but sort has 1"
```

线上跑的版本发出的游标是 1 值。新版一上线，**所有在途会话的下一页全部 400**。

更糟的是失败的形状：这个 400 被"诚实降级"层包装成 `"数据源查询失败"` 的告警——而那四个字在这个项目里是**下游熔断信号 + 计费豁免判据**，等于部署会给下游刷一批熔断事件、同时给自己免单。与此同时 `next_cursor` 变空，调用方以为翻完了 —— **正是这次改动本来要消灭的那种静默截断**。

三层测试都没抓到，原因是同一个：测试进程里只有新版代码，它发出 2 值游标、也只消费 2 值游标，自洽得很。

讽刺的是，同一份代码里已经有一段专门为"部署跨越期的在途会话"写的温和降级逻辑（旧游标只出声不报错）——作者（我）想到了这个场景，却没想到自己这次改动制造了同一个场景的新变体。

## 做法

**测法**：写一条测试，手工拼出**上一版格式**的状态，喂给新代码。

```python
def test_legacy_one_value_cursor_never_produces_a_doomed_request():
    legacy = base64.urlsafe_b64encode(
        json.dumps({"sa": [12345], "p": "..."}).encode()).decode()   # 上一版形态
    spec, r = run(cursor=legacy)
    assert spec.tiebreaker is None          # 本页退回旧形态，自洽走完
    assert "重新发起查询" in " ".join(r["warnings"])
    assert "查询失败" not in " ".join(r["warnings"])   # 绝不能碰熔断/豁免文案
```

**修法**，按优先级：

1. **先对账再发请求**。组装请求前校验状态与当前实现是否兼容，不兼容就让这一次按状态自身的形态自洽走完，**绝不发出注定失败的请求**。让下游的硬错成为可达路径，是设计缺陷不是运行时意外。
2. **让形态稳定**。能做到"新旧长度/字段数恒定"就别让它随路由结果浮动——本例最终让排序字段恒为 2 个，把"跨请求参数变了导致形态翻转"这个稳态故障也一并消掉了，只剩部署跨越期一个明确的过渡场景。
3. **让状态自描述**。把版本或关键参数写进状态本身（`{"sa":…, "p":…, "tb":"rowkey"}`），解码时以状态为准，能同时挡住部署跨越和"翻页中途改了查询参数"。

**验法**：部署后立刻用手工构造的旧格式状态打一次线上。本例的线上冒烟：

```
③ 部署跨越期: 旧版形态的 1 值游标
   拿到 20 条 | next_cursor: 有
   warnings: ['分页机制已升级，本页可能存在少量重复或遗漏；如需精确结果请不带 cursor 重新发起查询']
   触发熔断信号: 否 ✅
```

## 适用范围

- 适用于：任何由调用方持有并回传的状态，格式发生变化时
- 尤其适用于：MCP / Agent 场景——LLM 客户端持有游标的时间跨度不可控，可能横跨多次部署
- 不适用于：纯服务端状态（session 存在自己库里），那是数据迁移问题，另一套方法
- 注意：灰度/多副本发布下这不是"过渡期一次性问题"，而是**持续存在**直到旧副本全部下线
