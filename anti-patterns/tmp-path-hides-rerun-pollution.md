# 反模式：每次都给新目录的测试，永远测不到「重跑第二次」

## 一句话结论

`pytest` 的 `tmp_path`（以及一切"每个用例发一个空目录"的 fixture）让被测代码**永远在干净地面上起步**。凡是把产出物写进固定位置的功能，它的绝大多数真实运行都是第二次、第三次——而那些运行的输入里有上一次的残骸。测试套件全绿和"重跑不出事"是两件独立的事，后者要专门造一个"目录里已经有上次产物"的用例才测得到。

## 场景

- 功能会把文件写进一个**由输入决定、而非随机生成**的目录（`workspace/<片名>/`、`dist/`、`output/<job_id>/`）
- 产出的文件名带序号、带内容摘要，两次运行的参数不同就会产出不同的文件名
- 用户的正常用法就包含"改改参数再跑一遍"

## 踩坑经历

视频剪辑工具 cutmap 二期（2026-08-03）。`build_package` 把 LLM 产出的方案落地成一包切好的视频素材，分 `01_主片/` `02_切片/` `03_备选素材/` 三个目录，文件名形如 `切片1_三个真实处罚案例_05分05秒.mp4`。

这个模块前后过了**五轮实现 + 审查 + 修复**，最后 225 个测试全绿，覆盖了路径逃逸、字段为 `null`、容器不是列表、列表元素不是 dict、数值倒置、超长文件名等一大批脏输入。

然后做端到端验收：用真实原片跑了两次，两次的方案不同（切片条数和标题都变了）。第二次跑完，`02_切片/` 里是这样：

```
切片1_103家上市公司补税91.64亿_01分52秒.mp4     11:07  ← 上一次的
切片1_三个真实处罚案例_05分05秒.mp4              11:27  ← 这次的
切片2_某知名社交平台补了5点多个亿_02分13秒.mp4   11:07  ← 上一次的
切片2_跨境电商五大原罪_03分08秒.mp4              11:27  ← 这次的
切片3_三个真实处罚案例_05分05秒.mp4              11:07  ← 上一次的
切片3_合规到底还挣不挣钱_07分32秒.mp4            11:27  ← 这次的
切片4_偷税到什么程度会坐牢_05分57秒.mp4          11:27  ← 这次的
```

**序号撞车**：三个「切片1」「切片2」「切片3」各有两份。用户全选拖进剪辑软件，拿到的是新旧混杂的素材，而且从文件名完全看不出哪个是新的。

225 个测试一个都没响，因为它们全都长这样：

```python
def test_xxx(tmp_path, monkeypatch):
    package.build_package(Path("x.mp4"), tmp_path, plan, [], [])
```

`tmp_path` 每次都是一个崭新的空目录。**没有任何一个用例在"目录里已经躺着上次的产物"这个前提下跑过。**

更值得记的是这个功能的定位：这个工具的卖点之一就是"改方案重跑很快（转写有缓存）"，**改方案重跑是最常见的操作**。测试覆盖不到的恰恰是最高频的路径。

## 解法

1. **专门写一个「脏地面」用例**：先在 `tmp_path` 里造几个上次的产物（名字要跟这次会产出的**不一样**，否则被覆盖就看不出问题），再跑，断言旧文件不存在了。

   ```python
   def test_重跑时产出目录被整个重建不留旧文件(tmp_path, monkeypatch):
       old = tmp_path / "02_切片" / "切片1_上次的标题_00分10秒.mp4"
       old.parent.mkdir(parents=True); old.write_bytes(b"stale")
       package.build_package(..., tmp_path, plan_with_different_clips, ...)
       assert not old.exists()
   ```

2. **同时断言"清理不许越界"**：在同一个目录里放几个中间产物/缓存文件（转写结果、配置），跑完确认它们**还在**。清理逻辑最容易犯的第二个错是删过头——把重算代价高昂的缓存一起清了。

3. **清理失败不要静默**：`shutil.rmtree(..., ignore_errors=True)` 会吞掉"文件被其他程序占用""权限不对"这类真实失败，然后代码照常往下写新文件——用户又拿到一个混杂目录，而且这次连时间戳都不好排查（他以为清理逻辑已经修好了）。删完要**验证目录真的不存在**，还在就抛一个说人话的异常。

4. **判断标准**：如果一个功能的产出路径是"由输入决定"而不是"随机生成"的，它就需要这类用例。反过来，如果每次运行都写进一个带时间戳/UUID 的新目录，那 `tmp_path` 的语义恰好对得上，不需要。

## 教训

- `tmp_path` 是在**模拟一个从来不会发生第二次的世界**。真实系统的绝大多数运行都发生在自己上一次留下的痕迹之上。
- 五轮审查抓住了所有"输入是脏的"，一次都没想到"**地面**是脏的"。审查者和实现者都在盯输入数据的形状，没人盯运行环境的状态。
- 这类缺陷有个共同特征：**只在第二次运行时显形，而演示和验收往往只跑第一次**。真跑两次的成本很低，收益是发现测试套件结构性看不见的一整类问题。
