# 反模式：对方修好那天，把 `it.fails` 改成 `it` 就算翻正

## 一句话结论

一条**预期失败**的测试（`it.fails` / `xfail`）在等待期间**从未真正执行过它断言之后的世界**：它的输入怎么生成、它读的计数器有没有被别的跑次污染、旁边的注释描述的是不是旧现实——这些在"反正会失败"的日子里全部隐形。翻正那天只改一个关键字，等于把一条从没跑通过的测试直接放进 CI，红的时候你分不清是上游又坏了还是测试本身从来就没写对。

## 场景

- 契约守卫/集成测试里有一条按"对方承诺"写的断言，对方尚未实现，先用 `it.fails` 挂着等它自己转红
- 对方某天修好了，测试开始通过，`it.fails` 反而判失败——需要翻成正常断言
- 那条测试依赖外部状态：幂等窗口、共享账本、时间桶、跨跑次的计数器

## 踩坑经历

touch2-engine 的易查云契约守卫（2026-09-08）。上游把幂等语义对所有档位打开后，`it.fails("同键重放应带「幂等键命中」warning 且只扣一次费")` 需要翻正。只改关键字的话会带着三个洞上线：

| 洞 | 在 `it.fails` 时代为什么看不见 | 翻正后的表现 |
|---|---|---|
| 幂等键按**小时**截断（`guard-2026-09-08T06`），上游幂等窗 24h | 断言反正会失败，键长什么样无所谓 | 同一小时内跑两次（PR 推一次再 re-run、或撞上定时跑），第二次的**首发**已经是重放，credits 差 0 → **假红** |
| 读的是整把 key 近 7 天的用量流水，不分跑次 | 同上 | 定时跑与 PR 跑时间重叠，对方的两发算进本次差值 → 差 2 → **假红** |
| 邻居文件里三处注释写着"那条 `test.fails()` 继续按预期失败＝继续绿，没有任何人会被提醒" | 描述的是旧世界，当时是对的 | 翻正后**反了**：形状漂移现在会让它红——但红的措辞指向"幂等坏了"，误导排查方向 |

前两条是冷审（干净上下文子 agent）抓的，第三条也是——作者会话自己一个都没看见，因为作者的注意力全在"怎么让它绿"。

原注释还写着按小时截断的**理由**：「键里带日期粒度，避免与 24h 窗口内的历史调用互相干扰」——这句话本身是反的（小时桶隔离不了 24h 窗口，反而保证同小时内两次跑同键），但因为当年无害，没人核过。**写下过理由的决定不等于对的决定，只等于翻它时要先把旧理由驳掉再动。**

## 正确做法：翻正清单

翻 `it.fails` → `it` 之前逐条过：

1. **输入重新推导**：这条测试自己造的每个输入（键、时间戳、样本名），在"断言真会执行"的前提下是否跨跑次唯一？同一次跑里两发共用一个键 ≠ 每次跑用同一个键——前者是要验的东西，后者是撞窗口。
2. **它读的每个计数器是否按跑次隔离**：账本、用量、缓存命中数。不隔离的写进注释挂到后续卡，别假装没看见。
3. **连跑两次**：re-run 是最常见的撞窗口路径，本地就能复现。
4. **grep 引用它的注释**（`test.fails`、`expected fail`、用例名），把描述旧世界的话一起翻过来——尤其是"没人会被提醒"这类**方向性**陈述，翻正后往往反转。
5. **在上游真机复现断言的每一半**再翻：这次两条断言分别验响应面（warning 在）与账本面（差 1），后者对 internal 档成立是因为流水记标价不扣余额——不核这一条，翻过去可能换一种红。
6. PR 正文写清**这条从此会咬人的旧洞**（第 2 条那种）挂到哪张卡，别让下一次假红又变成"红了没人看"。

## 适用范围

- 适用于：任何带外部依赖的预期失败测试（契约守卫、集成、e2e），尤其是断言涉及幂等、计量、时间窗口的
- 不适用于：纯函数单测的 xfail——那种翻正确实只是改关键字
