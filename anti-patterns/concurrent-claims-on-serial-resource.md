# 串行资源上的并发申领：两个 PR 各自从 0003 开始，本地都绿、CI 也都绿

## 一句话结论

多个分支同时向一个**带序号的仓库级账本**（迁移编号、changelog、ADR 编号、平台生成的索引文件）申领下一个号时，冲突只在合并那一刻显形，而在此之前**每个参与者在自己那侧看到的都是完全合法的状态**——单 PR 视角和 CI 都发现不了，只有横向比对能发现。

## 场景

审查 PR 时（人审或 AI 审），默认视角是「这个 diff 对不对」。绝大多数问题确实在单个 diff 里，但有一类不在：**它在两份 diff 的交集里，而交集不属于任何一个 PR。**

## 详细说明

### 踩坑过程

同一天有两个 PR 同时动数据库 schema，作者是两个人：

- PR A：认证与租户（三表 + RLS），4 条 drizzle 迁移
- PR B：billing 域（14 表 + 触发器 + RLS），4 条 drizzle 迁移

main 上的迁移到 `0002` 为止。两人都基于同一个已合并的基座往前做，各自跑 `drizzle-kit generate`，**双方都拿到了 `0003`–`0006`**：

| | PR A | PR B |
|---|---|---|
| 0003 | `0003_tenancy_auth.sql` | `0003_billing-domain.sql` |
| 0004 | `0004_rls.sql` | `0004_append-only-triggers.sql` |
| 0005 | `0005_invitation.sql` | `0005_allocation-cap-guard.sql` |
| 0006 | `0006_invitation_rls.sql` | `0006_rls-policies.sql` |

两边还都改了 `meta/_journal.json`，各带四个同名 `meta/000X_snapshot.json`。

**双方本地全绿，两个 PR 的 CI 也全绿。** 因为 CI 只跑「当前分支 vs main」的合并结果，从不跑「两个待合分支互相的合并结果」——后者在 CI 的世界观里不存在。

### 为什么后果比普通冲突严重

普通文件冲突可以手工解。但 drizzle 的 snapshot 是**链式**的：每份 snapshot 基于前一份生成，`_journal.json` 记录顺序。后合的那个 PR **没法手工解冲突**，必须整个重新生成迁移（改编号为 `0007`–`0010` 并重跑生成器）。

如果没在审查阶段发现，暴露点会是：先合的那个进去了，后合的那个作者在 rebase 时面对四个巨型 JSON 冲突——而他此时已经在等合并、心态最急的时候。

### 怎么发现

**同时有多个 open PR 动同一个带序号账本时，先横向比一次编号。** 一条命令的事：

```bash
for n in $(gh pr list --state open --json number --jq '.[].number'); do
  echo "PR #$n:"
  gh pr view $n --json files --jq '.files[].path | select(test("migrations/"))'
done
```

把结果做集合比对，有交集就是冲突。

### 同类资源清单

不止数据库迁移，凡满足「仓库级 + 单调序号 + 生成器自动取下一个」的都有这个问题：

- 数据库迁移编号（drizzle / prisma / alembic / flyway）
- ADR / RFC 编号
- changelog 的 unreleased 段落
- 平台生成的索引文件（`_journal.json`、`.lock`、路由清单）
- 端口号、feature flag key、错误码这类需要全局唯一的常量

### AI 协作特有的部分

**AI 审 PR 时天然是单 PR 视角**——工具接口就是「给我一个 PR 号，我读它的 diff」。这个视角下，上述冲突是**结构性不可见**的，不是「不够仔细」能弥补的。

对应的做法是：审查流程里显式加一步「横向扫描」，不依赖 AI 在读单个 diff 时灵光一现。触发条件也很好判断——**只要 open PR 数 > 1 且它们碰了同一个目录**，就跑一次横向比对。

这条也是「容易查的观测量回答的不是真正要问的问题」的又一个实例：**单 PR 绿**容易查，但要回答的问题是**这批 PR 合并后仓库还成立吗**。

## 数据支撑

- 发现方式：同一场会话中连续审四个 PR，在读第二个的文件清单时与第一个撞上；**若分两次会话审，大概率漏掉**；
- 两个 PR 各自的 CI：全绿；
- 两位作者本地：全绿；
- 若漏掉的返工成本：后合方需重新生成 4 条迁移 + 4 份 snapshot（无法手工解冲突）。

## 适用范围

- **适用于**：任何多人/多 agent 并行且存在仓库级单调序号资源的项目；并行度越高、单 PR 越大，越容易撞；
- **不适用于**：单人串行开发（每次只有一个 open PR 时不存在此问题）。
