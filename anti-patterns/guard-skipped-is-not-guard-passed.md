# 反模式：守卫「一格都没判」与「判过了都合格」，在输出上是同一个样子

> 来源：TOUCH 2.0 界面改版 C6（2026-09-18），合并一个 PR 时
> 结果：一次受管写动作绕过了守卫的五条判据，读到提示时已经合完

## 一句话结论

文本匹配型守卫有**三种**结局：放行 / 拦下 / **根本没认出这是受管动作**。第三种在终端上与第一种逐字相同——命令照常执行、没有多余输出。而把命令写成一个语义等价、词法不等价的形状（命令替换、多行、前缀赋值、额外空白），就足以把动作移出它的识别窗口。

⇒ 判据一句：**守卫文档给了字面形态，就照抄那个形态，别自己"等价改写"**——你以为的等价是语义等价，守卫吃的是词法。

## 场景

- PreToolUse hook / pre-commit / CI 里按**命令文本**做模式匹配的守卫（「这条命令必须带某某声明才放行」「这个动作必须走那个封装函数」）
- 让 LLM 代理执行这类命令。它会很自然地把硬编码值换成 `$(...)`、把单行拆成多行、在前面加一条 `cd` —— **每一种改写单看都是好习惯**
- 守卫的「不适用」分支没有任何输出，或者有输出但不拦

## 踩坑经历

一道守卫要求：合并 PR 时必须声明「我核过的是哪棵树」，写成 `verified=<字面 sha>`，且 `gh` 要在命令位起点。我写的是把 sha 现取出来——

    verified=$(git rev-parse HEAD) gh pr merge <N> --squash

看起来更严谨（sha 不会抄错），实际上：`$(...)` 让这段不再是守卫认的 `NAME=VALUE` 赋值段，`gh` 前面于是只剩一个空格——而空格**不在**它的命令位分隔符集合里（那是刻意的，否则散文里「用 gh pr review 的时候……」也会被收进来）。结果是它**没把这条认成受管动作，五条判据一格都没判**，合并直接过去。

拿真守卫的识别函数对六种写法实跑（`classifyCommands` / `extractVerifiedSha` / `looksGuardedButUnmatched`）：

| 写法 | 认出受管动作？ | 取到 verified= | 结局 |
|---|---|---|---|
| `gh pr merge N --squash  # verified=<sha>` | ✅ 1 个 | `<sha>` | 五条判据照判 —— **文档推荐的那个形态** |
| `verified=<sha> gh pr merge N --squash` | ✅ 1 个 | `<sha>` | 照判 |
| `cd /repo` 换行 + 上一行 | ✅ 1 个 | `<sha>` | 照判 |
| `verified=$(git rev-parse HEAD) gh pr merge N --squash` | ❌ | `null` | 🔴 **一格都没判** |
| `cd /repo` 换行 + 上一行（代理的默认形态） | ❌ | `null` | 🔴 **一格都没判** |
| `verified=$(...) && gh pr merge N --squash` | ✅ 1 个 | `null` | 拦下（`no_verified_sha`）—— 安全侧 |

注意最后两行的对比：**只差一个 `&&`**。`&&` 在分隔符集合里，于是 `gh` 回到命令位，动作被认出来、声明取不到、干脆利落地拦下。少了那两个字符，整道闸静默让开。

### 这道闸其实装了第三只眼，而它救不了这一格

守卫里有一个 `looksGuardedButUnmatched`：命令里出现了受管子命令、却没被认出来时出声提醒。实测上表第 4、5 行**它确实响了**。但它走的是 PreToolUse 的 `additionalContext` / `systemMessage`，**不是 deny**——命令照跑，提示与工具结果一起回来。等你读到「我没把它认成受管动作，所以一格都没判」时，PR 已经合了。

⇒ **「出声」和「拦下」是两回事。** 一道会漏判的闸，补一个提醒只把事故从「不知道」变成「事后知道」；要真的拦，提醒得出在能拦的位置上。

### 最贵的是失败方向，不是失败次数

同一族错误（写法把动作挪出识别窗口）此前发生过三次，**三次都是 deny**：闸拦下来、报文告诉你该怎么写、代价为零，而且你当场就学会了正确形态。这一次是 skip：没拦、没报错、什么都没发生。

**fail-closed 的守卫每失败一次都在教你；fail-open 的守卫每失败一次都在骗你。** 所以评估一道闸不能只问「它拦得准不准」，要问「它认不出来的时候会怎样」。

## 正确做法

1. **照抄文档给的字面形态。** 上表第一行那种「命令在前、声明写成行尾注释」的形态最稳：它不依赖赋值段规则，读起来也直说「这是声明，不是环境变量」。
2. **给守卫的「不适用」分支一个出口，并想清楚它出在哪。** 只打日志等于没有；`additionalContext` 只能事后知道；要拦就得 deny。
3. **便宜的预筛不能比真判据窄。** 同一道闸常见的形状是：shell 里先用字面子串快速预筛，匹配上才起进程跑真判据。预筛窄一点点，窄掉的那部分就是**连"没认出来"都不会说**的静默漏判。预筛宁可宽。
4. **事后对账。** 受管动作的执行记录 × 守卫的判定记录，对不上的条数就是漏判数。这件事只能事后做，但它是唯一能发现「静默漏判」的办法。
5. **把每次绕过写成常驻用例。** 每一个绕过形态都值一条测试——因为它证明了识别窗口的边界在哪，而边界只有被撞过才知道。

## 适用范围

- 适用于：一切按**文本**判定的守卫——命令 hook、pre-commit、lint 规则、CODEOWNERS 路径匹配、CI 里的 `if: contains(...)`
- 适用于：让 LLM 代理执行带守卫的命令（它改写命令的频率远高于人，而每次改写都是一次识别窗口的赌博）
- 不适用于：在**被保护对象一侧**强制的机制——数据库约束、文件权限、平台 ruleset、git 自己的分支锁。那一类没有「没判」这个状态，要么允许要么拒绝
