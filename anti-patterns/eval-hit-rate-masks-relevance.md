# 反模式：用"非空率"当检索评测标准——宽匹配把 1.0 刷满，掩盖全错的结果

## 一句话结论

检索类功能的评测如果只断言"返回非空"，**匹配逻辑坏得越宽，指标越好看**：错误的 OR 分词匹配让每个查询都命中一堆无关结果，评测线显示 1.0 满分，事故在生产里跑了一个月才被下游用户发现。成功标准必须包含**正确性断言**（top-1 结果与查询的可判定关联），"命中率"三个字里必须有"命中的是对的东西"。

## 场景

- 搜索/检索/匹配类功能建评测线，成功标准写成 `len(results) > 0`
- 底层匹配是分词 OR 语义（ES match、SQL LIKE 多条件 OR、向量近邻无阈值）
- 评测显示满分，但没人抽查过返回内容和查询是否相关

## 踩坑经历

贸易数据 MCP（2026-08-12）。企业库支持按官网域名反查公司，真实查询评测线显示 `domain.all` 层命中率 **1.00（20/20）**，一直被当作"已验证能力"写进对外材料。

下游 AI 实际使用时发现不对：查 `otto.de`（德国最大电商之一）返回的是突尼斯汽配公司和香港贸易行；查 `dunelm.com`（英国家纺连锁）返回深圳一家贸易公司。原因：`{"match": {"website": query}}` 是 OR 分词——`otto.de` 被切成 `[otto, de]`，任一 token 命中即返回，于是**一切含 `.de` 的网站都算命中**，`meta.total` 高达 10000+。

评测为什么满分：宽匹配保证了每个域名查询都"非空"。**匹配越错，非空率越稳定在 1.0**——指标最好看的时候恰是功能最坏的时候（同族问题见 `green-metric-measures-wrong-mechanism`：那篇是故障态让指标回到正常值，这篇是评测标准从未测量过要保证的性质）。

修复分两半，缺一不可：

1. 功能修复：`match` → `match_phrase`（要求 token 相邻），实测 `otto.de` 从 1 万+垃圾变 442 条相关，top-1 就是 Otto 本尊；
2. **评测标准修复**：`domain.all` 层的判据从 `data 非空` 改为 `data 非空 且 top-1 的 website 字段包含查询域名(归一化后)`。改完真实评测从虚假的 1.00 变成诚实的 **0.85**（3 个 miss 是真实未收录的域名）——数字变难看了，但第一次变得可信。

## 解法

1. **每层评测写标准时问一句：什么样的坏实现能把这个指标刷满？** 答得出来就说明标准有洞。"非空"能被无条件返回全库刷满，就绝不能单独当标准。
2. **正确性断言要可判定、可自动化**：检索域名 → 结果字段包含查询串；检索公司名 → 归一化后 token 重叠；不必完美，够卡住"完全无关"即可。
3. **指标变难看是修复成功的证据**：1.00 → 0.85 的那 0.15 是原本被掩盖的真实缺口，留在报告里，别调标准把它调回满分。
4. 修复此类问题时同步修两处：功能代码 + 评测标准。只修功能，下一个同类 bug 还是会被满分掩盖。
