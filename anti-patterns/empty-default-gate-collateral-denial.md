# 反模式：用「默认空授权」关掉一批付费功能——同一道闸后面的零成本能力被一起关掉，而拒绝不留痕

## 一句话结论

需求是「某类用户**不开付费项**」，实现写成「这类用户的授权集**为空**」——两者在写下的那天等价，此后随着闸门里的项变多而悄悄分叉：挂在同一道闸上的自有、零成本能力，也跟着变成「这类用户不可用」。如果说明文档恰好让 AI 第一步就调这项能力，**这类用户的每一次多步骤任务都从一次拒绝开始**；再加上拒绝发生在预检层、不计费、不落账本、不打日志，影响面是 100%，信号是 0。

## 场景

- 有一道按「授权项」判定的闸门（entitlement / feature flag / OAuth scope），**同一个集合里装着两类项**：要花钱的第三方能力，和需要单独管控的自有能力；
- 为了让免费号 / 试用号不开付费项，选了最省事的实现：新建账户时授权集为空（默认拒绝），零代码；
- 后来又有能力挂到了同一道闸上，或者早就挂着但写需求的人没想起来；
- 被拒的请求在预检层就返回了：不计费、不写账本、不打日志。

## 踩坑经历

- 可方法论剧本 `get_playbook` 早在更早的薄片就挂了 `required_entitlement="playbook"`。剧本是我方自有能力，零外部成本，却被空授权一起关了。

## 为什么没人发现（三个可迁移的机制）

### 1. 「空集」表达的是「一个都不给」，不是「不给付费的」

需求说的是后者，实现选了前者，因为前者不用写代码。两者在需求提出那天恰好等价，之后随着闸门里的项增加而分叉——**分叉本身没有任何代码变更触发**，所以没有 diff 可评审。新项挂上闸门的那个 PR 在另一条线里，写它的人不知道有人用「空」来表达「免费」。

### 2. 拒绝发生在预检层，不留痕

预检拒绝不计费、不写账本、不打日志。事后能查「谁没有这项授权」，查不了「谁因此被拒了」：账本只记放行的调用，被挡掉的那次调用在任何数据里都不存在。所以这个问题只能靠读代码推出来，无法从运营数据里被发现。

### 3. 指令和授权各管一半，互不校验

说明和技能是写给 AI 的指令（「先调它」），授权是对账户的限制（「不许调」）。两者由不同薄片、在不同时期写下，谁也不检查对方——指令要求的第一步，对某一类账户恰好是必拒的一步。

## 替代方案

- **把默认集显式写出来，不要用空集表达「免费」**：本例改为 `SELF_SERVICE_DEFAULT_ENTS = ("playbook",)`，只在建户那一刻写入。测试里意图的两半各写一条断言：「默认恰好有 playbook」「三把付费授权一把都没有」，而不是一条「为空」。
- **给闸门加新项时，就是检查点**：新增 `required_entitlement` 的那个 PR 里，逐个账户类型过一遍「默认会不会拿不到它」。
- **对指令里的「第一步」做可达性检查**：对外说明点名要 AI 必调的工具，逐个账户类型确认它们调得通。能自动化就写成守卫：各账户类型的默认授权 × 说明里点名的必调工具。
- **拒绝要留痕**：预检拒绝至少按「工具 × 拒绝原因 × 账户类型」计数，否则「授权门挡住了多少人」永远是未知数。
- **修复后的存量回填**：只追加、不覆盖；按命名空间限定范围；默认 dry-run；单事务，出错整体回滚。并声明「部署当天一次性」——日后再跑，会把运营后来故意撤掉的授权加回来，因为回填分不出「故意没给」和「从来没给」。

## 适用范围

- 适用于：任何授权集、功能开关集、OAuth scope **同时装着付费项和自有能力项**的系统；用「默认为空」来表达「某类用户不开某些功能」的地方；对外说明会指定「先调某个工具」的 Agent / MCP 服务。
- 不适用于：闸门里只有一类项，而且今后新增的项必然也属于「付费才开」——那时默认空就是正确语义。
