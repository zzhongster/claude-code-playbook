# 反模式：改共享样式时漏掉另一个消费者，未定义的 `var()` 会让整条声明作废

## 一句话结论

CSS 里引用一个**不存在**的自定义属性，浏览器不会回退到默认值，而是把**整条声明当作无效丢弃**（`background: var(--gone)` 等于这行没写）。所以删掉一个变量、而另一个文件还在引用它时，页面不会报错、不会变红、控制台一片安静——只是某个颜色悄悄没了。改共享样式表的人往往只验证自己那个页面，第二个消费者要等很久才被撞出来。

## 场景

- 一个 `style.css` 被多处消费：服务端渲染的结果页、静态入口页、组件内联样式
- 重做配色/改设计时重命名或删除 `:root` 里的变量
- 代码审查看的是"改动后的那个页面长什么样"，没人把所有消费者列一遍

## 踩坑经历

视频剪辑工具 cutmap 二期（2026-08-03）。页面重做时把 `style.css` 的配色变量整套换掉，`--accent-fg` / `--accent-bg` 这两个删了。

但 `index.html`（拖拽入口页，跟结果页是两个文件）里还有：

```css
#fill { background: var(--accent-fg); }        /* 进度条的填充 */
#drop.over { border-color: var(--accent-bg); } /* 拖拽悬停态 */
```

后果：**进度条填充色变成透明**。任务在跑、百分比在涨、宽度在变，用户什么都看不见——一个长达几分钟的处理过程，进度条看上去永远是空的。

这个 bug 活过了**两轮代码审查**。原因很具体：审查拿到的是"页面重做"这个任务，看的是 `render.py` 生成的结果页；`index.html` 是上一期就有的静态入口页，不在这次 diff 里，没人想到去看它。直到下一个任务做流水线接线时，实现者为了验证进度反馈才起了服务，一眼看出进度条是空的。

**同一个形状在同一个项目里复发了一次**。后来加「上次用过的脚本」提示区时：

```css
.hidden { display: none; }
#prev-script { display: flex; }   /* id 选择器权重更高 */
```

一个文件都还没拖，这块提示就露在首屏上——规则写了 `.hidden`，安静地不生效。跟前一次一样：**声明存在、意图明确、结果是零**。

## 解法

1. **加一条纯静态断言，20 行就够**：把所有源文件里的 `var(--xxx)` 引用提取成集合，跟 `:root` 里定义的集合做差集，非空就失败。同一个脚本顺手做 class 的版本——渲染代码里发出的 `class="..."` 全集 ⊆ 样式表定义的全集（这条在同一个项目里当场扫出两个"发了但没定义"的 class）。

   ```python
   def test_所有css变量引用都有定义():
       defined = set(re.findall(r"--([\w-]+)\s*:", css))
       used = set(re.findall(r"var\(--([\w-]+)", css + html + js))
       assert not (used - defined)
   ```

   这类断言便宜、快、不需要浏览器，能拦住"发了没接"这一整类。

2. **改共享资源前先列消费者**：`grep -rn "var(--" --include="*.html" --include="*.js" --include="*.css"`。删变量这个动作的影响面天然是全局的，但 diff 只显示局部。

3. **审查任务书里点名**："这次改的是被 N 处消费的共享样式表，列出所有消费者并逐个确认"。审查者不会自己想到去看不在 diff 里的文件。

4. **权重问题同理**：id 选择器 (100) 压过 class (10) 是规范行为，但"我写了 `.hidden` 它却不隐藏"和"我写了颜色它却透明"是同一种体验——**规则存在但结果为零**。工具类要么用 `!important`，要么保证不被 id 选择器覆盖。

## 教训

- CSS 的失败模式是**静默降级为零**，不是报错。这跟大多数语言相反，也是它特别容易在审查里滑过去的原因。
- 审查的视野边界是 diff。**被删掉的东西的消费者不在 diff 里**——这是 diff-based review 的结构性盲区，只能靠静态断言或显式点名来补。
- 两次事故都不是"想错了"，是"没想到要看那里"。这类问题不该靠人更细心来防，该靠一条跑得飞快的静态断言。
