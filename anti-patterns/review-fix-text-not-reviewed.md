# 反模式：处置评审发现时写下的那段「订正」，自己没被审——而它最容易错

## 一句话结论

评审提出一条发现，你改完并**顺手写下一段解释「原来错在哪、以后怎么办」**（注释、文档、反例条目、PR 描述）。那段解释是**新写的、没被任何人读过的断言**，而它恰恰在你刚被证明判断失误的那件事上做陈述——**两次实测里两次都带着新的事实错误**，且都要等下一轮冷审才被抓出来。

⇒ 判据一句：**「改完 = 这条关闭」在有解释性文字的处置上不成立。带文字的处置要重新进审，和第一版代码一样。**

## 场景

- 工作流要求「评审发现逐条处置：改 / 不改 + 理由」，且处置常常连带写下经验总结（反例库条目、注释、runbook、PR 描述里的处置表）；
- 用干净上下文子 agent 做冷审，作者自己处置（AI 协作里这是常态：发现与处置由同一个上下文完成）；
- 处置的内容包含**对过去时刻的事实陈述**：「当时脚本显示 X」「这几份文件都改了」「某某卡上已经裁过」。

## 踩坑经历

TOUCH 2.0，2026-09-17/18，一张设计 token 卡（实现 PR + 归档 PR）。两个 PR 各跑三轮干净上下文冷审，**每轮都只审增量**：

| PR | 轮次 | 审的是什么 | 结果 |
|---|---|---|---|
| 实现 #2592 | 1 | 首个提交 | 1 挡合并（判据册旧值没同步）+ 5 建议 |
| | 2 | **上一轮的处置提交** | **1 挡合并**：处置里新写的「文字副本名单」把一处**没改**的文件列得像已改；另有一条「这组测试一处都管不到」与同文件断言自相矛盾 |
| | 3 | 上一轮的处置 | 0 挡合并，收敛 |
| 归档 #2605 | 1 | 归档 + 反例条目 | 1 挡合并（反例条目的处方与时间线不符）+ 4 建议 |
| | 2 | **上一轮的处置提交** | **1 挡合并**：订正后的处方把兄弟卡写成「没开工」，而它当时已开工、已改真源——脚本看不见它是另一个原因 |
| | 3 | 上一轮的处置 | 0 挡合并，收敛 |

**两个 PR，两次「处置提交」，两次都在处置里引入了挡合并级的事实错误。** 而两次的形状一样：**我在描述「我当时为什么错」时，对当时的状态做了一个没核过的陈述**——一个把没改的文件写成改了，一个把已开工的卡写成没开工。归档 PR 首轮那条挡合并也是同一形状（一条刚写好的反例条目，把「脚本当时本可以发现」写反了），只是它出现在首版而不是处置里。

原因不难理解：处置那一刻手里只有「刚被指出错了」这个印象，而写下的是对当时环境的重建。**印象最强、证据最弱的时刻，恰好是要求你落笔的时刻。**

## 正确做法

1. **把「重新进审」写进流程，不靠自觉**：处置完提交后，从第一步重跑冷审，直到某一轮**零新增「改」**为止（touch2-engine 的 `/pr` §3 第 4 步就是这句，这次照做才收敛）；
2. **每轮只喂增量 + 上一轮的发现与处置**，成本比首轮低得多（本次第三轮分别只用了 1–4 分钟）；
3. 写事实陈述时**当场取证**：时间戳去会话记录/提交历史取，「这几份文件都改了」去 `git diff --name-only` 取，「脚本当时显示什么」把那次输出贴出来——凡是写了「实测 / 现取」的，让审查者能复核；
4. 审查 prompt 里**点名要它核处置本身**（「上一轮发现是 A，处置写成了 B，请核 B 是否属实」），而不是泛泛「再看一遍」；
5. 分组写名单时把状态写进组名（「本次改了」/「本次没改、仍是旧值」），比在项目后加括号更难写错——本次第一版就是括号形态，读者会当成已改。

## 数据支撑

- 6 轮冷审（两个 PR 各 3 轮），挡合并项共 **4 条：2 条在首版里，2 条在处置文字里**；
- **处置提交的挡合并命中率 2/2**——每一次处置都引入了一条；
- 按句子类型分：4 条里 **3 条落在「重建当时状态」的散文句**上（一条首版的反例条目 + 两条处置），只有 1 条是普通的漏改（判据册旧值）。⇒ 危险的不只是「处置」这个时机，是**凡是回头描述过去状态的句子**；
- 收敛轮（零新增改）两次都出现在第 3 轮。

## 适用范围

- 适用于：AI 作者 + AI 冷审的工作流；处置带解释性文字（反例库、注释、runbook、PR 描述）；
- 不适用于：纯机械修复且不写任何解释（改一个常量、补一个 import）——那种处置没有新断言，重跑门即可；
- 注意：这不是「多审几轮总没坏处」。**第三轮之所以值得跑，是因为第二轮的挡合并项是第一轮处置引入的**；零新增改就停，别把它变成无限循环。
