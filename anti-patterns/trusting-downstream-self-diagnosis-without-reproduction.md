# 反模式：直接采信下游 AI 客户端的自诊断报告，不用真实调用独立复现就去改服务端

## 一句话结论

下游 AI 客户端（另一个 Agent/Copilot/助手）报"你的服务/工具用不了"时，它给出的**症状描述**通常是真的，但它给出的**根因归因**往往不可信——因为它在诊断时同样缺乏对自己客户端内部实现（工具发现机制、schema 加载、参数序列化）的可见性，容易把"我这边有问题"误诊成"你那边挂了"。拿到这类报告的第一反应应该是**用真实调用独立复现**，而不是直接信任报告里的结论去改服务端代码。

## 场景

- 你维护一个被多个不同 AI 客户端/Agent 平台接入的服务（MCP server、API、SDK）
- 某个下游客户端（尤其是非官方生态、你没有直接调试权限的那种）反馈"你的某个功能不可用"，并附带了它自己跑出来的"诊断报告"
- 报告写得有条有理、甚至带了"实测覆盖率""API 状态：正常"这类看似严谨的自查小节，容易让人产生"它已经排查得很彻底了"的错觉

## 踩坑经历

2026-08-27，用户转述了豆包办公（字节跳动 AI 办公助手）对 trade-agent-data 项目 trade-data MCP 的一份自诊断报告，结论包括：

1. `analyze_market` 工具"多个工具描述里提到，但搜索未返回，可能当前环境未暴露"
2. `search_trade`/`find_buyers` 等工具的 schema"只有 `{"type": "object"}`，没有具体参数定义"
3. 用 `origin_country`/`destination_country` 等参数试了多种组合，`filters_applied` 始终为空
4. 结论：`analyze_market` 无法调用，其余工具因 schema 缺失无法构造有效查询

报告本身逻辑自洽、语气笃定（"API 可用，覆盖 71 个市场""注意到中国不在数据市场列表中"），如果直接采信，下一步大概率是去检查服务端的工具注册逻辑、schema 生成代码，排查"为什么 `analyze_market` 没暴露出去"——一个根本不存在的服务端问题。

## 独立复现

在同一个会话里用同一套 trade-data MCP 服务端直接验证：

- `describe_market("cn")` → 中国确实不在提单级市场列表（这条报告说对了，是设计使然）
- `analyze_market`（默认参数）→ **直接拿到了真实数据**，schema 完整（`search_trade` 实测有 20+ 个具体参数）——与报告"无法调用/schema 缺失"的结论**直接矛盾**

进一步比对报告里提到的参数名 `origin_country`/`destination_country`，在真实 schema 里根本不存在（真实参数是 `origin`/`destination`）——这个细节直接证伪了"schema 缺失导致猜参数"之外的另一种可能（比如"文档写错了"），坐实是报告方在没有真实 schema 的情况下凭描述文字猜的参数名。

## 根因（为什么下游的自诊断会系统性地把锅甩给服务端）

下游客户端诊断"工具用不了"时，能看到的只是**它自己那一层**发出去的请求和收到的响应；它看不到（也没法看到）：

- 自己的 MCP 客户端在 `tools/list` 阶段是否完整拉取了 schema，还是做了截断/摘要
- 自己是否有一套"先搜索再加载 schema"的延迟工具机制，以及这套机制的搜索/匹配逻辑是否命中
- 自己的模型在缺 schema 时，是不是在"凭工具描述文字猜参数名"

这些环节全部发生在下游自己的技术栈里，它没有能力（也没有动机）怀疑自己，于是"看起来最合理"的归因就是"对方服务端有问题"——尤其当它自己还跑了几个"确认可用"的 API 调用（如报告里的 `get_balance`/`describe_market`）作为佐证时，会显得诊断很严谨，但那些调用恰好是不依赖完整 schema 就能凑出参数的简单工具，掩盖了"复杂工具因 schema 缺失而调用失败"这个真问题。

## 修复 / 应对方式

收到下游自诊断报告后，标准动作是：

1. **先分类**：报告里哪些是"我方系统的客观状态"（如"某市场没有数据"），哪些是"下游对我方内部机制的推测"（如"schema 缺失""工具未暴露"）——后者必须独立验证，不能采信。
2. **用真实调用复现**：直接调对应工具，对比报告里的"复现步骤"和"实际返回"，尤其关注报告里点名的具体参数名是否在真实 schema 里存在。
3. **拼症状找根因**：多条症状（"搜不到某工具" + "schema 退化成空对象" + "用了不存在的参数名"）如果指向同一类底层机制（如"客户端没正确拉取 schema"），比逐条单独解释更可信。
4. **诚实记录不确定性**：没有下游客户端内部实现的直接访问权限时，根因判断只能是"推断，非直接证据"，如实说明，不要把推断包装成定论。

## 验证方法

下次收到"你的服务/工具用不了"类报告，先问自己：报告里的关键结论（尤其是"某工具不可用""参数不生效"这类否定性结论）有没有被独立复现过？如果只是转述了下游的自查结果就要动手改代码，先停下来用真实调用测一遍。

## 适用范围

- **适用于**：任何被多方/多客户端接入的共享服务（MCP server、开放 API、SDK），尤其是接入方的技术栈你无法直接调试时
- **不适用于**：接入方能提供可复现的原始请求/响应日志（而非自己的诊断结论）时——这种情况下原始日志本身就是一手证据，可以直接分析，不需要"独立复现"这道额外工序
- **更通用的教训**：任何"A 系统报告 B 系统有问题"的场景，A 的症状描述值得信任，A 的根因归因需要独立验证——A 对自己内部机制的盲区，恰恰是它最容易甩锅给 B 的地方
