# 反模式：为消掉一次闪烁去清共享 state，把别处没保存的用户输入一起卸了

> 来源：TOUCH 2.0 界面改版 C6 收件箱空状态（2026-09-18）
> 结果：第二轮冷审提出闪烁、我加了一行清空、第三轮冷审逮回来，已撤回，未进 main

## 一句话结论

`setX(null)` 长得像一个局部动作，实际上它的代价要按**最贵的那个消费者**算。一个被两个以上分支读的 state，清空它可能让另一棵子树卸载重挂——而重挂对渲染和网络请求都是无害的、可重来的，**唯独对组件内 state 里那点用户手打的文本不可恢复**。

⇒ 写下 `setXxx(null)` 之前先数一遍消费者，并单独问一句：**有没有用户输入会被丢？**

## 场景

- 列表 + 详情两栏布局：收件箱、邮件客户端、文件管理器、IDE、后台管理页
- 切页签 / 换筛选时，为了不让用户先看到上一次的结果而清空列表
- 详情栏里有**未提交的输入**：回复框、表单草稿、编辑中的单元格、注释输入
- 评审提出的是一条**真实存在**的小瑕疵，而处方的作用面比问题大

## 踩坑经历

收件箱空状态改版。第二轮冷审提了一条不挡合并的建议，措辞很准：

> 切到「全部」后，列表数据还是「待回复」那次取回的空数组。在新数据回来之前，会先闪一下「回信会出现在这里」，而上一屏刚告诉用户「你有会话」。

处方看着很小、很自然——换页签时先把列表清成 `null`，让它显示骨架：

```tsx
useEffect(() => {
  setRows(null);      // ← 这一行
  void load();
  const t = setInterval(() => void load(), LIST_POLL_MS);
  return () => clearInterval(t);
}, [load]);
```

**代价是第三轮冷审才逮到的**：`rows` 不只喂列表，右栏线程也从它推——

```
rows → visible → current → ThreadPane
```

`rows = null` ⇒ `current = null` ⇒ `ThreadPane` 走早返回的占位分支 ⇒ `ThreadView` 与 `ReplyComposer` **卸载重挂**。而 `ReplyComposer` 的输入框是组件内 state：

1. **用户打了一半、还没发出去的回复，当场丢**；
2. 每次换页签多拉一次 messages（而卡面明写「不改已有的 API 调用逻辑」，属于被动踩到）；
3. 换来的也不是「不闪」——中栏改成闪一下「选一条会话查看线程」。

改动前旧 `rows` 还在，含选中会话时中栏纹丝不动。**净效果是把一次无害的闪烁，换成了一次数据丢失。**

错在哪：**我把「这个 state 喂谁」当成了「这个 state 喂列表」。** 决定清空之前没有回答「谁在读它」——而那一步只要 `git grep` 一下 `rows` 就能看见 `current` 也在读。冷审那条建议本身是对的（闪烁真实存在），错的是**处方的作用面比问题大**。

## 机器一道都逮不住

`tsc`、eslint、全套 e2e、29 道本地门全绿。全仓 e2e 没有「开着详情栏切页签」的用例——而这类用例很少有人写：它要求测试同时持有两个状态（**选中项** + **未提交的输入**），而后者通常被当成实现细节。逮住它的是第三轮冷审顺着 `rows` 的消费者链读下去。

⇒ 这类「小修」今天的守门人只有冷审，所以它值一条目。

## 正确做法

1. **动共享 state 之前先列消费者。** 判据一句：**「清掉它」不是一个局部动作——凡是被两个以上分支读的 state，清空的代价要按最贵的那个消费者算**（这里最贵的是用户手打的文本，不是一次渲染）。
2. **代价里单独问一句「有没有用户输入会被丢」。** 重挂组件在 React 里是常规操作，唯独输入框不是——它是这次唯一不可恢复的东西，渲染与请求都可以重来。
3. **真要修这类闪烁，别清数据，给数据打上它属于哪次筛选的标签**（`{tab, rows}`）：列表按标签不符画骨架，`current` 仍从旧结果里找。这样闪烁没了、详情栏也不卸载。
4. **收益与代价不对称时就撤回。** 这条本来就是改动前既有的行为、不在卡面范围内——**不在范围内的顺手修，一旦代价超过收益，第一选择是撤回，不是加大改动去补救。**
5. 撤回时把推理写进代码注释和 PR 描述。下一个人会再想到同一个「小修」，注释是唯一拦得住他的东西。

## 适用范围

- 适用于：React / Vue / Svelte 等**靠挂载与 key 决定组件生命周期**的框架，尤其「清空父 state ⇒ 子树卸载」这条链
- 也适用于：任何「重置缓存 / 清会话 / 重新初始化 / 换租户就清空」的动作——问的是同一句「谁在读它」
- 不适用于：确实只有一个消费者的局部 state（那时清空就是局部动作）
