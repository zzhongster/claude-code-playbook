# 反模式：在 A 副本的会话里改 B 副本的 hook 脚本，`cd` 过去跑一遍当作验过了

## 一句话结论

宿主解析 hook 脚本的路径**在会话启动时就锁死了**（Claude Code 是 `CLAUDE_PROJECT_DIR`），`cd` 到另一个工作副本不会改变它。于是「改了 B 副本的 hook → 切过去跑一次 → 没反应」的失败现象，与「我代码写错了」**完全一致**：零报错、零输出、零记录。而你刚改完代码，第一嫌疑人必然是自己写的那几行——**于是你回去改一份本来正确的实现**。

## 场景

- 多工作副本并行：一任务一 clone、或 `git worktree` 一分支一目录（AI 辅助开发下这是常态，因为多个会话要同时开工）
- 宿主用「项目根目录」变量解析配置与脚本：Claude Code 的 `.claude/hooks/*`、编辑器的项目级插件、pre-commit 的本地钩子、devcontainer 的生命周期脚本
- **你改的是 hook 脚本本身**，不是被它调用的业务代码

三个条件同时成立时才会撞上。少了第三条不会——业务代码是当前 `cwd` 解析的，`cd` 过去就是新的。

## 详细说明

### 踩坑经历

2026-08-08，给一套协作工具埋点补 4 个 `.mjs` 入口（卡号 TOU-71，同一套埋点的另一个坑见文末「相关」）。

工作副本是 `touch2-a`（会话所在）和 `touch2-b`（改动所在）。改完 `touch2-b/.claude/hooks/usage-log.sh`，26 条离线用例全绿，于是验真实链路：

```bash
cd ~/work/touch2-b && node tools/diff-budget/run.mjs   # 命令正常执行，退出码 0
tail -3 ~/.claude/usage/touch2.jsonl                   # 没有这一条
```

命令跑了、没报错、埋点一条没记。**触发的是 `touch2-a` 上 main 的旧脚本**——它只认 `*.sh` 结尾，压根不认识 `.mjs`。

hook 的配置长这样，问题就在这一行：

```json
"command": "{ H=\"${CLAUDE_PROJECT_DIR:-$PWD}/.claude/hooks/usage-log.sh\"; ... }"
```

`CLAUDE_PROJECT_DIR` 是**会话启动时**注入的，指向启动会话的那个目录。`cd` 只改变被执行命令的 `cwd`，改不了这个变量。

### 为什么这个坑比一般的「配置没生效」更黏人

三种原因的现象完全相同：

| 真实原因 | 现象 | 你会怎么想 |
|---|---|---|
| 代码写错了 | 无记录 | **第一嫌疑**（刚改完） |
| hook 根本没被触发（matcher 不匹配） | 无记录 | 第二嫌疑 |
| **加载的是另一个副本的旧代码** | 无记录 | **想不到** |

离线用例全绿本该把第一种排除掉。但人在这一刻的实际反应不是「那一定是别的原因」，而是「**用例大概没覆盖到真实情况**」——毕竟离线用例是自己写的，真实链路才是权威。这个推理方向听起来完全合理，它把你直接推向去修改一份正确的代码。

我当时正是这么想的，只是先去确认了「hook 到底加载了哪个文件」，才没动那几行。

### 解法

1. **改 hook 脚本后，真实链路验证必须在改动所在的那个副本里另起会话**——或者先把改动合进主干，再让各副本拉取（本次走的后者，合并后在原会话拉一次就验通了）。`cd` 过去不算数。

2. **排查顺序反过来：先确认加载的是哪个文件，再怀疑代码。** 最省事的办法是在脚本顶部临时插一行 marker：

   ```bash
   echo "$(date +%s) loaded: ${BASH_SOURCE[0]}" >> /tmp/which-hook.log
   ```

   路径不是你以为的那个，后面所有推理都不用做了。

3. **分清两种「改动」的生效范围，它们完全不同：**

   | 改什么 | 同一副本内 | 跨副本 |
   |---|---|---|
   | 脚本**内容** | **当场生效**（每次调用重新执行文件） | 永不生效 |
   | 配置里的**路径** | 当场生效 | 永不生效 |

   「配置改动当场生效、不用重启会话」这条经验是对的——但它只在**同一个副本内**成立。跨副本时它反而是有害的：它让你以为「既然当场生效，那我改完就该看到效果」。

4. **给 hook 脚本留一套「直接喂事件 JSON」的离线用例。** 它不依赖 hook 触发，在任意目录、任意副本都能跑。没有它，每改一行都要开新会话才能验，验证成本高到最后没人验——而 hook 恰恰是最不该失去验证的那类代码（它跑在宿主进程里，错了会静默影响所有人）。

## 数据支撑

| 项 | 值 |
|---|---|
| 撞上所需的条件 | 3 个同时成立（多副本 / 宿主按项目根解析 / 改的是 hook 自身） |
| 失败现象与「代码写错」的可区分度 | **0**——退出码、stdout、stderr、落盘结果四项全同 |
| 离线用例状态 | 26 条全绿（正确地指向「不是代码问题」，但直觉会反过来解读） |
| 定位成本 | 确认加载路径 1 分钟；不确认而去改代码，改的是正确实现，无上限 |

## 适用范围

- **适用于**：任何「宿主在会话/进程启动时锁定项目根，再据此解析脚本路径」的场景——Claude Code hooks、编辑器项目级插件、devcontainer 生命周期脚本、按项目根查找的 git 钩子
- **尤其适用于**：`git worktree` 或多 clone 并行开发。AI 辅助开发下多会话并行是常态，这个坑的触发频率比单副本时代高得多
- **不适用于**：改的是被 hook 调用的业务代码（那部分按 `cwd` 解析，`cd` 过去就是新的）；单副本工作流（不存在「另一个副本」）
