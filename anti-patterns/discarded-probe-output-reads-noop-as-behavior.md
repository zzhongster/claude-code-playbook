# 反模式：丢掉动作的返回值，只看下游状态——于是把"根本没执行"读成了"被测对象的行为"

## 一句话结论

把探针/动作调用的输出重定向进 `/dev/null`（或干脆不看），只观察下游状态有没有变，那么**"调用压根没生效"和"被测对象就是这个行为"在你眼里完全同形**。观察到"没变化"时，人的第一反应是给被测对象编行为模型，而不是怀疑自己那一枪是空的——连开三枪都没动静，会让这个错误模型更可信，而不是更可疑。

## 场景

- 用 CDP / Playwright / adb / API 客户端驱动一个界面或服务，靠"下游状态是否变化"判断成败
- 循环里批量发同一类调用，为了输出干净加了 `> /dev/null` 或 `-s` 静音
- 命令拼接方式换过（heredoc、变量插值、参数编码方式），但没有回头验证过"新拼法真的把载荷送到了"

## 踩坑经历（2026-09-04，trade-agent-data / WorkBuddy 连接器发布页）

要在一个级联下拉里逐个查看三个一级分类的二级选项。写了个 shell 函数，循环三次，每次 `curl` 把一段 JS 发给 CDP proxy 的 `/eval` 执行点击，然后读右列内容：

```bash
curl -s -X POST "http://localhost:3456/eval?target=$TID" --data-urlencode "@/dev/stdin" <<EOF > /dev/null
(function(){ ...点击 "$CAT"... })()
EOF
sleep 1
curl ... # 读右列
```

三次右列内容一模一样，都是初始分类的二级列表。于是我得出结论：**"点击没生效，这个 React 级联菜单大概是 hover 展开的"**，接着花了两轮去手工派发 `mouseover`/`mouseenter`/`pointerover`——全都无效，因为方向从一开始就是错的。

真相是那三次点击**一次都没执行**：`--data-urlencode "@/dev/stdin"` 把 JS 当成表单字段编码，proxy 收到的不是可执行代码，每次都返回 `{"error":"Uncaught"}`。而这个返回值被 `> /dev/null` 吃掉了。改回 `-d '(function(){...})()'` 直传后，第一次调用就正常返回。

代价：两轮无效的事件派发实验 + 一个凭空捏造的组件行为模型。而排除它只需要不写那个 `> /dev/null`。

## 根因

1. **静音的是"动作是否发生"，观察的是"世界是否改变"——这是两个命题。** 后者为假，前者未必为真。只测后者，就把"没开枪"和"枪打不穿"合并成了同一个观察值。
2. **重复不产生新信息。** 三次调用共享同一个坏拼法，是同一个错误重复三遍，不是三个独立证据。但人对"连续三次都这样"的直觉是"这是稳定现象"，于是错误结论被加固。
3. **改了调用形式却没有重新验证通路。** 前一次调用用 `-d` 直传是成功的，切成 heredoc 是为了拼接变量方便——形式一变，通路默认要重新证明，而不是继承上一次的信任。
4. **失败是软的。** proxy 对坏载荷返回 200 + `{"error":"Uncaught"}`，不是非零退出码。`set -e`、`|| exit` 这类护栏一个都不会响。

## 修复 / 正确做法

**1. 动作的返回值一律留在视野里，哪怕只截前 100 字节。**
输出太吵就截断，不要丢弃：

```bash
curl -s -X POST ".../eval?target=$TID" -d '...' | head -c 120   # 而不是 > /dev/null
```

调用返回体里通常直接写着 `error`——本例的 `{"error":"Uncaught"}` 出现在第一次调用里，看见它就不会有后面两轮。

**2. 每种新的载荷拼法，先跑一发"必然可见"的探针再进循环。**
比如先发 `1+1` 或 `document.title`，确认回的是 `2` / 真实标题，再把真正的动作塞进同一个拼法里。换 heredoc、换编码参数、换转义方式，都要重来一次——这一发的成本是几秒。

**3. 观察到"没变化"时，先问"这一枪出膛了吗"，再问"打在哪了"。**
顺序不能反。给被测对象编行为模型（"它大概要 hover"）是最贵的一步，把它放在通路验证之后。

**4. 循环里的失败要能自己出声。**
批量调用时把返回值 grep 一下错误关键字，命中就中断，别让 N 次失败静静滑过去：

```bash
resp=$(curl -s ... ) ; case "$resp" in *'"error"'*) echo "FAIL: $resp"; break;; esac
```

## 反模式信号

- 命令行里出现 `> /dev/null` 或 `-s` 之后，紧跟着一句"没反应"式的结论
- "试了三次都不行" —— 三次用的是同一个调用拼法吗？那是一次
- 开始给被测对象编行为模型（"它可能需要 hover / 需要焦点 / 有防抖"）时，回头看：你有没有一条证据证明动作本身送达了
- 调用形式刚改过（heredoc、引号、编码参数、转义），紧接着出现"从这以后就不工作了"

## 适用范围

- **适用于**：任何"发动作 → 看下游状态"的验证回路：浏览器自动化、adb/模拟器、CI 里调 API 改状态、给守护进程发信号、DB 写入后查读
- **尤其适用于**：软失败的通道（HTTP 200 里塞 error 字段、退出码恒 0 的 CLI、吞异常的 SDK）
- **不适用于**：动作与观察是同一次调用的同一个返回值（那时没有"两个命题"的裂缝）
