# 反模式：花钱的外部调用结果只放内存，修完 bug 就整轮重跑

## 一句话结论

批处理里凡是按次计费的外部调用（邮箱验证、联系人查询、号码核验、付费搜索），**结果必须在拿到的那一刻落盘**，重跑时先查盘再调用。只放在进程内存里的结果，一次「修个小 bug 重跑一下」就会被整轮重新购买——而且没有任何报错提醒你钱又花了一遍。

## 场景

- 一个多步骤的数据管线（找人 → 取邮箱 → 第三方验证 → 出表），中间某一步调用付费 API
- 前几步的上游调用已经有缓存（比如联系人库结果落了 SQLite），这一步却是后加的，图省事用了内存 dict：`SNOV = {}`
- 第一版跑完发现一个与这一步无关的 bug（比如人名匹配错了），修完直接 `python step3.py` 重跑

## 踩坑经历（2026-10-19，海外公司名单补联系人）

第 3 步对约 130 个邮箱做第三方验证（Snov，按次计费），结果存在模块级 `SNOV = {}` 里。出表后发现越南人名匹配邮箱有 bug（`hung.nguyen` 挂错人），修完整个第 3 步重跑——联系人库的调用走了 SQLite 缓存没花钱，**Snov 的 130 次验证全部重新买了一遍**。之后又加了个「把还没出结果的再验一次」的补验，才想起该落盘。

最终账单：Snov 约 290 次调用、去重后只有 138 个邮箱，约 37 元是纯浪费，占这单总成本的近三成。

同一个项目里还有第二个同形问题：邮箱挖掘服务（免费但**每次返回不完全一样**）没落盘，重跑时一个上一轮已验证有效的邮箱没再出现，该公司的联系人数从 2 掉到 1，交付表悄悄变差。

## 为什么容易犯

- 管线是逐步加出来的：最早的步骤认真做了缓存，后加的步骤「先跑通再说」
- 重跑的触发点往往是**别处的 bug**，注意力不在这一步上
- 付费调用的成本在账单里，不在终端输出里；重跑「成功」了，没有任何信号

## 怎么做

1. **结果到手就写盘**：`dict` → 每批结束 `json.dump`；或直接用 SQLite，键是请求的规范化参数
2. **区分「确定结果」和「临时结果」**：只缓存确定的（valid / invalid / unknown），`pending`、超时、限流这类不缓存，下次重查——否则会把临时失败永久化
3. **非确定性的免费源也落盘、取并集**：每次返回不同的服务（挖掘、搜索），历次结果合并保存，避免重跑让结果变少
4. **重跑前先问一句**：这一步里有没有按次计费、且结果只在内存里的调用？有就先补落盘再重跑
5. **成本报告里单列重复调用**：调用次数和去重后数量放在一起报（「290 次 / 138 个」），浪费一眼可见
