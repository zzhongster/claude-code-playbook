# 生产发布交给用户在终端跑，Claude 读终端输出逐项核对

## 一句话结论

当 Claude 的会话不能直接连生产机（权限检查拦 ssh、或者就不该给），不要退化成「把一长串命令贴给用户、各凭运气」。把发布写成**一个带自检的脚本**（干跑确认 → 核对现有配置 → 唯一镜像 → 替换 → 冒烟 → 失败自动回滚 → 只读探针），用户在终端执行一条命令，Claude 用读终端的工具逐行核对输出、判断每一步是否真的成功。人负责授权与按键，脚本负责安全，Claude 负责核对。

## 场景

- Claude Code 自动模式下，`ssh root@<生产机>` 被以「Production Reads」拒，`gh pr merge` 在用户没对该 PR 明确授权时被以「Merge Without Review」拒。
- 生产机有来源 IP 白名单，只有用户所在网络能连。
- 同一类服务要反复发布（一周内 admin-svc 发了 5 次）。

## 详细说明

trade-agent-data（2026-10-27 ~ 29）的做法，最终收进 `scripts/ops/deploy_admin_oauth.sh`：

1. **本机部分**：确认 PR 已合并（不是就退出，什么都不改）→ 发布 origin/main，合并后 main 又前进了就列出新增提交、要求输入 yes → `git archive` 导出干净源码 → rsync 干跑列出删除项、要求输入 yes 才真同步（排除 `.env*`、令牌、`.git`）→ 经 `ssh … bash -s < 远端脚本` 执行远端部分 → 公网冒烟。
2. **远端部分**：核对源码树就是本次提交（`.deploy-sha`）→ 核对现有容器的端口、挂载（必须恰好是账本卷）、启动命令、`-e` 额外变量与模板一致，任何不符就中止 → 构建唯一 tag → 逐个替换：旧容器改名保留，冒烟失败自动回滚；改名失败或找不到备份时不删现有容器 → 只读探针（真调一次第三方接口，确认凭据、IP 白名单、可见范围）→ 只列不改的数据检查（dry-run）。
3. **Claude 的角色**：给出那一条命令；用户跑完说「跑完了」，Claude 用读终端工具拿到输出，逐项核对（构建成功、冒烟 200、探针 ok、dry-run 清单是否符合预期），发现异常再给下一条命令（例如 dry-run 列出了意外的数据，先讲清楚再给 `--execute`）。
4. **涉密配置**：要往生产 `.env` 写 Secret 时，脚本在本机读密钥文件、经 ssh 标准输入传过去，Secret 不出现在命令参数、进程列表或聊天里，两端只回显长度用于比对。

## 实测中它挡住的事

- 用户在本机直接跑了本该在生产机上跑的 `docker run`（缺 `ssh` 前缀）：只是失败，没有副作用；Claude 读终端发现后补上正确命令。
- 用户在 PR 还没合并时就跑了部署：脚本第一步退出，什么都没改。
- 合并后 main 被别的 PR 推进：脚本列出多出的提交，Claude 核对它们不影响本次服务后才让用户确认。
- 冒烟里 `Connection refused` 一行看着吓人：Claude 能从完整输出看出那是容器启动期的等待、随后 200，避免误判回滚。
- dry-run 清单里出现了不该有的数据（全选把主账号的额度也设了）：在执行写库之前被发现，先修代码再清理。

## 适用范围

- 适用于：Claude 不能或不应直连生产、但发布频繁且步骤固定的服务；用户能在自己的终端执行命令，且会话有读终端的能力。
- 不适用于：需要交互式排障、步骤每次都不同的事故处理（那需要人直接操作或临时授权）；不能读终端输出的环境（那就只能让用户贴回输出）。
- 验证情况：目前只在 trade-agent-data 一个项目里用过（5 次 admin-svc 发布、1 次含 oauth-svc），按本仓库规则 pattern 需两个项目验证，第二个项目用过后补充。
