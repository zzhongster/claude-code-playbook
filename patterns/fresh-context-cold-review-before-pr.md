# 提 PR 前的干净上下文冷审（Fresh-Context Cold Review Before PR）

## 一句话结论

PR 审查里真正干活的不是「另一个人」也不是「更强的模型」，是**干净上下文**——把这道冷读前置到作者侧（新开子 agent 只喂 diff + 判据），大部分问题在提 PR 前就被消化，人审从「第一发现人」退回「裁决与抽查」位。

## 场景

- 团队全员用 CC 开发也用 CC 审 PR，出现「作者的 CC 没发现、审查者的 CC 一读就发现」的怪象；
- 人审排队成为交付瓶颈（「当天审完」压力大、审查者对不熟的代码只能橡皮图章）；
- 想给「自己验证过」一个可检验的证据形态，而不是一句「跑过了」。

## 详细说明

做法（五步，已固化进 touch2-engine 的 `/pr` 命令 §3）：

1. `git fetch origin`；分支落后 main 先变基/快进跟上，再取两点 diff——不跟上，别人已合的代码会混进待审内容（落后时两点 diff 的「删除」全是别人的新增）；
2. **新开干净上下文**（子 agent 即可），只喂三样：diff、完成判据（无卡/无 ticket 就写「本次改动要达成什么」清单）、涉及的规格章节。**不喂写码过程中的任何解释——解释一进去，上下文就不冷了**；
3. 要它产出发现列表：位置 + 问题 + 为什么是问题（可加红/黄/白分级）；
4. 作者逐条处置：**改**（改完提交后从第 1 步重跑，直到没有新的「改」）或**不改 + 一句理由**；
5. 「发现 + 处置」整段进 PR 描述；零发现也要写明「冷审零发现」——没有这段视为没冷审。

人审的角色随之变化而不是消失：对着「发现 + 处置」**裁决**（作者对自己的发现有动机偏袒，标「不改」的项恰恰最该被人看）、抽查证据、守红线；批准 = 背书的语义不变，签字自动化不了。

终止条件的实践经验：轮与轮之间发现会从「实质缺陷」收敛到「记录性修订」；红项清零、「改」级只剩措辞/记录类时可收口，在 PR 描述里写明收口理由。

## 数据支撑

- **touch2-engine（0811，本 pattern 落地的那个 PR 自身）**：作者会话自查后，五轮冷审（每轮全新上下文）抓出 2 红 10 黄，全部是作者自查未见——含被 `head -20` 静默截断的引用排查、伪引宪法原文、归档声称的跟进任务在外部系统查无实物；
- **trade-agent-data（另一项目，同机制不同位置）**：per-task 评审全绿的三个薄片，整分支独立终审各抓出一条 Important 级缺陷（见 [whole-branch-review-catches-emergent-defects](whole-branch-review-catches-emergent-defects.md)）——独立上下文是唯一不与被审内容共享盲区的验证层。

## 适用范围

- 适用于：任何用 LLM 会话产出、需要过审的交付物（代码、文档、配置、流程文件）；单人项目同样适用（没有人审时它就是唯一的审）；
- 不适用于：替代人审的裁决与背书；替代专项审计（schema/租户/账本这类按规格逐条比对的 auditor 查的是另一类问题）；对「实测才能暴露」的缺陷（性能、并发、真实数据规模）冷审是静态的，替代不了跑。
