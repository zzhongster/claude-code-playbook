# 配置层确认与端到端验证要分开记账

## 一句话结论

读回配置值只能证明**"配置写对了"**，不能证明**"功能生效了"**——两者之间隔着一条下发链路，而这条链路失败时通常不报错。验收清单里必须把它们拆成两条，**配置层那条你自己可以勾，端到端那条只能靠实测**，混成一条就会有"以为做完了"的假完成流进下游。

## 场景

任何"改平台/中间件配置，然后指望某个行为发生变化"的场景：

- 改网关超时、限流阈值、缓存策略；
- 改 DNS 记录、路由规则、防火墙策略；
- 改队列的可见性超时、重试次数；
- 云厂商控制台里任何"保存后生效"的开关。

这类操作的共同特征：**你能读回配置值，但配置值不是你真正想要的东西**——你要的是行为改变。

## 案例

### 案例一：Zeabur 网关 SSE 超时

产品硬要求「平台不能对 SSE 长连接施加短超时」。客服答复专属服务器的入口网关默认 600 秒、可自行调整，给了 GraphQL mutation。

执行并回读：

```graphql
mutation { updateServerIngressTimeout(_id: "...", serverTimeout: "24h") }
# → {"data":{"updateServerIngressTimeout":true}}

query { server(_id: "...") { ingressServerTimeout } }
# → 改之前：null（走默认 600s）
# → 改之后："24h"
```

看上去很完整：改之前有基线、mutation 返回 true、回读值正确、状态持久化。

**但这只证明了 Zeabur 的控制面数据库里存着 `24h`。**Traefik 有没有真把这个值下发到 ingress、一条 20 分钟不断的 SSE 连接到底能不能扛住——**当时机器上还没有任何服务，根本测不了**。

所以验收写成了两条：

```
✅ 网关超时已改 24h（执行 mutation 并回读确认）
   ——但这只是配置层确认，端到端能否扛住长连接要等 SSE demo 实测
[ ] SSE 端到端实测（归另一张卡，另一个人）
```

如果当时图省事勾成一条"网关超时已配置"，下游看到的就是"这条过了"，真正的风险要到上线才暴露。

### 案例二：Cloudflare DNS 记录

同一天的另一个系统，同样的形状，但后果更极端：API 返回 `success: true`、UI 正常显示、GET 读得回，**区文件里根本没写**，权威 NS 返回 NXDOMAIN。

如果只看控制面，三条记录"都配好了"。详见 [cloudflare-silent-dns-record-rejection](../anti-patterns/cloudflare-silent-dns-record-rejection.md)。

## 做法

**1. 验收清单里拆成两条，并写清楚各自的证据来源。**

| 层 | 证据 | 谁能出 |
|---|---|---|
| 配置层 | 回读 API / `dig` 权威 NS / 配置文件 diff | 改配置的人当场自证 |
| 端到端 | 真实流量下的行为观测 | 往往依赖别人的产出或真实环境 |

**2. 端到端那条如果依赖别人，就别挂在自己的卡上。**它依赖别人的产出，却卡在你的完成判据里 —— 这种排法会让两边都以为对方在推进。正确做法是把它挂到真正交付它的那张卡上，本卡只留配置层，并显式写出依赖关系和时间约束。

**3. 配置层确认要包含"改之前的基线"。**只看改之后的值，无法区分"我改生效了"和"它本来就是这个值"。上面案例里 `null → 24h` 这个前后对比，才让"我确实改了"成立。

**4. 措辞上别偷懒。**"已配置"和"已生效"在验收文档里是两个词，不要混用。写卡、写 PR 描述、写日报时都是。

## 为什么值得单独立一条

这类假完成有个共同特征：**当下没有任何东西报错**。测试是绿的、API 是 200、UI 是正常的，只有真实流量会暴露问题，而那通常已经是上线之后。

它也特别容易被"看起来很严谨"的动作掩盖——回读了、有基线了、状态持久化了，四个动作做下来很容易产生"我验证过了"的错觉。但这四个动作全都发生在控制面内部，一步也没跨到数据面。

## 适用范围

- 适用于：所有"控制面写入 + 数据面执行"分离的系统（云平台、CDN、网关、DNS、消息队列）；
- 不适用于：本地配置文件（改完即最终状态，无下发环节）；也不适用于改完能立刻在同一进程内观测到行为变化的场景。

## 证据强度

单次会话中两个独立系统（Zeabur 控制面 / Cloudflare DNS）的实例，来自同一个项目、同一天。**尚未跨项目复现**——收录是因为两个实例的失效形状完全一致，且第二个（Cloudflare）造成了实际的排查成本。跨项目验证后可提升置信度。
