# 模式：每个薄片上线后跑一次生产全链路探针——它抓的是单测原理上抓不到的回归

## 一句话结论

有一类回归，单元测试**在原理上**就抓不到：跨执行边界的上下文丢失、部署形态差异、真实中间件行为。解法不是写更多单测，而是把"上线后用临时凭证走一遍真实全链路"固化成每个薄片的收尾动作——几分钟成本，抓到的都是单测盲区里的真雷。

## 场景

- 改动涉及执行模型（线程池/进程/异步边界）、传输层、认证计费链这类"环境相关"代码
- 单测里这些边界被 mock 或根本不存在（单测同进程同线程直调 handler）
- 服务部署形态与本地不同（容器、反代、真实协议栈）

## 踩坑经历

贸易数据 MCP（2026-08-13），同一天两个案例：

**案例一（抓到 396 个单测全绿下的真回归）**：为解并发瓶颈把工具 handler 从事件循环移入线程池。全量单测过、压测过、部署后基础冒烟过。生产 E2E 走"开账户→发子密钥→真实扣费→查余额"全链路时，`get_balance` 返回"内部身份/无余额"——**contextvars 不会自动传播进 `run_in_executor` 的线程**，唯一在 handler 内读计费上下文的工具拿到了 None。单测为什么全绿：测试直调 handler，压根不经过 executor 边界；后补的回归测试必须专门构造"经 `_handle_call` 走线程池"的路径才能变红。修复是 `copy_context().run` 包裹。

**案例二（E2E 顺手暴露产品级盲区）**：同一轮 E2E 里发现名字带 "SUPPLY CHAIN" 的目标公司被货代过滤器默认滤掉、聚合结果里完全不出现——功能"正确"（过滤器就是这么设计的），但真实使用路径下用户会得出"查无此公司"的错误结论。这类"各组件都对、组合起来误导"的问题只有真实链路能暴露。

固化后的探针清单（该项目现行做法，每次部署后 2-5 分钟）：
- 用管理端开一把**临时 trial key**（真实计费路径，不是 internal 旁路）
- 真打生产端点：一次计费查询（验扣费+账本）→ `get_balance`（验上下文+余额回显）→ 特性相关探针（幂等键三连发验只扣一次 / 故障降级验免计费 / 子密钥验共享池）
- 校验点看**响应原文**（billing 块数字、warnings 文案），不看"有没有报错"
- 撤销临时 key，清理测试账户

## 解法

1. **识别"环境相关"改动**，强制生产探针收尾：执行模型、传输、认证、计费、序列化边界。纯业务逻辑改动可以只靠单测。
2. **探针用真实身份走真实计费路径**：internal/mock 旁路会跳过恰恰最该验的链路（案例一就是计费上下文丢失）。临时凭证用完即销。
3. **断言看数值和文案，不看状态码**："200 且没抛异常"抓不到"返回了错误的正常响应"（案例一返回的就是结构完全合法的错误答案）。
4. E2E 抓到回归后，**补一个能在单测层变红的最小重现**（案例一：构造经线程池的调用路径），让下次同类问题不用等到生产才发现——探针负责发现未知，单测负责钉死已知。
