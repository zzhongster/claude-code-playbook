# 模式：上游的占位值必须在自己这层清洗——"数据源给的就这样"不是放行理由

## 一句话结论

上游系统经常把"不知道/没收录"编码成**长得像数据的占位值**（哈希伪域名、"TO ORDER" 占位收货人、词典最近邻错配），而不是空值或报错。这类值能通过所有通用校验（非空、格式合法、HTTP 200），静默透传后下游会把它当证据用、甚至链式喂给下一步。修法永远是在**自己的边界**加一道领域不变量门：宁可诚实空，绝不透传假；且优先选"通用形状门"而非针对性黑名单。

## 场景

- 你的服务是数据管道中间层：上游（供应商 API/自建采集/第三方库）→ 你 → AI Agent 或人
- 上游对查不到的东西返回"看起来有内容"的东西，而不是 null/404
- 下游是会**链式消费**的 Agent：一条假数据会被当成证据写进报告，还会作为参数喂给下一个工具

## 踩坑经历（同一项目三例，2026-07~08）

**例一：哈希伪域名（最典型）**。"公司查官网"上游对未收录公司返回 `http://_<32位hex>_.com`——内部实体哈希包装成域名形状。我方未清洗直接透传：`isError:false`、五键齐全、data 非空、warnings 无害——下游研究 Agent 实测把它当 Bosch 官网写进报告归成 official_site 证据，还照工具链提示把假域名喂给"挖邮箱"继续挖，**一条假数据自走两跳**。下游合作方的原话值得刻下来："问题定在『我方没做清洗就透传』，不是『数据源给的就这样』"。
修法：**RFC 合法主机名门**（下划线在主机名里本就非法）——占位符天然全拦，还顺带堵住了内部哈希外泄的黑盒缺口。通用形状门比"匹配 `_hex_` 就删"的针对性过滤强：上游哪天换个占位格式，只要还不是合法域名就照样拦。

**例二：提单占位收货人**。海关数据里 "TO ORDER"/"TO THE ORDER OF..." 是提单惯例占位（凭指示交货），不是真实买家。按采购商聚合排名时它们混进名单高居前列——用户拿到的"Top 买家"里坐着一个法律术语。修法：占位收货人变体名单过滤（这类惯例占位是有限枚举，黑名单合适）。

**例三：词典最近邻错配**。中文品名查英文标准名，ES match 召回的"最像的那条"被直接采信——"回声"配出 Echo Dot、"宠物瓶"配出 PET 瓶。修法：**召回≠命中**，match 召回后客户端全等复核，过不了宁可返回未命中。同族做法后来复用于"海关名撞企业库"（归一化全等才认，防同名错绑）。

## 解法

1. **对上游的每类"查无"行为做实测画像**：查一个肯定不存在的东西，看它返回什么。返回的不是空/错而是"内容"，这就是占位值，登记形态。
2. **门放在自己边界，用领域不变量表达**：合法主机名、合法邮箱、金额非负、日期可解析、名称归一化后全等——不变量门天然覆盖未知的占位变体；只有当占位是有限惯例枚举（如 TO ORDER）时才用黑名单。
3. **过滤要出声**：`data` 只留真值，warnings 写明"N 条为无效占位记录，已过滤，不作依据"。静默删除和静默透传是同一枚硬币——下游无法区分"没有"和"被吞了"。
4. **诚实空≠故障**：占位过滤后的空结果是"查无"（照常计费/正常语义），不能落进故障降级分支（免计费/熔断信号）——两条路径的 warnings 文案要可区分（本项目：故障含"查询失败"，过滤含"已过滤，不作依据"），下游按文案分流。
5. **链式入口同门复检**：占位值可能从别的路径绕回来（用户手输、下游把旧结果当参数）——消费该类型参数的每个工具入参处放同一道门。
6. 长期解是推动上游返回诚实空，但在那之前：**你放出去的每个字段，你负责**。

## 关联

- 反模式 `eval-hit-rate-masks-relevance`：非空≠有效——评测层的同一个教训（拿"返回非空"当通过判据，正好被占位值骗过）。
- 模式 `user-facing-copy-is-machine-contract`：过滤警示与故障降级的文案分野一旦被下游用作计费/熔断分流，就是契约，逐字钉死。
