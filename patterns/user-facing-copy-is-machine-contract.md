# 模式：一旦下游用文案做程序判断，人类可读文案就是 API——按契约管理它

## 一句话结论

错误提示、warning 措辞这些"给人看的文案"，在集成方开始用前缀匹配做重试/熔断/计费判断的那一刻起就变成了**机器契约**——改一个措辞等于改 API 签名。识别出这类文案后要做三件事：测试逐字钉死、写进项目红线文档、承诺变更前知会下游。

## 场景

- 协议/框架没有结构化错误码（如 MCP 工具错误只有 `isError:true` + 文本），下游只能靠文案分类错误
- 自己系统内部用 warning 字样做分支判断（计费豁免、降级标记）
- 集成方是另一个团队/公司，他们的解析逻辑你看不到

## 踩坑经历

贸易数据 MCP × TOUCH 2.0 集成（2026-08-13）。MCP 协议层错误没有结构化错误码——HTTP 恒 200，错误是 `result.isError:true` + 文本。对接确认时 TOUCH 明确了他们的三分类处置逻辑全靠文案：

- `"请求过于频繁"` 前缀 → 退避重试
- `"Token 余额不足"` 前缀 → 停发+告警
- warnings 含 `"查询失败"` → 熔断（区别于真查不到）

同时我方自己也把 `"查询失败"` 字样用作**计费豁免判据**（数据源故障降级不收钱，靠扫 warnings 识别）——同一串文案同时是下游熔断信号和我方扣费分支条件。此时任何人"顺手润色提示语"都会同时弄断两边。

对方的洞察也值得记：**fixture 测试锁的是"我们以为对方会返回什么"，只有真调用锁的是"对方实际返回什么"**。他们为此建了"契约守卫测试"——定期真打一次上游，专验文案前缀、响应结构、幂等行为。守卫红了不代表代码坏了，代表上游契约漂了。

我方对应的管理动作：
1. 单测把各故障降级路径的文案统一含 `"查询失败"` 钉死（防各工具文案漂移导致计费豁免失效）；
2. 项目 CLAUDE.md 增设"对外契约红线"章节，列明三样机器契约（限流/余额文案前缀、五键响应结构、`"查询失败"`/`"幂等键命中"`/`"本次未计费"` 字样），标注"改动=破坏性变更，必须提前知会"；
3. 给下游的契约文档里所有报文形状用**生产实测原文**，不用文档推断——对方照抄的就是真实行为。

## 解法

1. **盘点哪些文案已被程序消费**：自己代码里 `if "xxx" in warnings`、集成文档里"按文案前缀识别"——找到的每一条都升格为契约。
2. **逐字钉死**：契约文案的断言用全文/前缀精确匹配，不用"含关键词大概齐"；测试注释写明"下游按此前缀做程序判断，改动需走变更通知"。
3. **红线文档化**：写进项目级 CLAUDE.md/CONTRIBUTING，让不知情的后来者（包括 AI 会话）在改提示语前撞见警告。
4. **建议下游做契约守卫**（真调用、低频、专验契约面），并把自己的联系渠道写进去——守卫红了应该找你对，而不是猜。
5. 长期解是推动结构化错误码，但在协议支持之前，承认现实：**文案就是接口，按接口的纪律对待**。
