# 实验：高频追加文件的三种写法 × git 合并冲突（一条一文件是唯一无冲突解）

日期：2026-08-10 ｜ 场景：touch2-engine 反例库改造（TOU-165）｜ 方法：`git merge-tree --write-tree` 三组对照

## 问题

团队高频写入的单一共享文件（changelog、反例库、job 注册表、速查表）会变成**全员合并路径上的固定冲突点**：约定「新条目加顶部」使所有并行分支的 diff 落在同一行号区间，两两必然 `changed in both`，而解法永远是机械的「两边都留」——每次都有唯一正确答案、却必须人工做一遍。实测一天之内同一文件撞两次、一条 PR 连撞三轮（main 每前进一次就再冲突一次）。

## 实验

小仓库造 base 文件，从同一 base 切两条独立分支，各按同一写法加一条，`git merge-tree --write-tree A B` 判冲突：

| 写法 | 结果 |
|---|---|
| 两分支都在**顶部**插入（原约定） | **冲突** |
| 两分支都在**末尾**追加 | **冲突** ——两边 hunk 锚在同一文件尾，与顶部插入完全对称 |
| 两分支**各新增一个文件** | **无冲突**（100% 自动合并） |

随后在真实仓库全流程复验：改造合入后，两条同 base 分支各加一个条目文件、先后合入 main，第二条 `mergeable=MERGEABLE / mergeStateStatus=CLEAN`，零冲突解决动作。

## 结论

1. **「末尾追加天然可以自动合并」是常见误解**——git 三方合并对「两边都在文件末尾追加」照样报冲突（经典 changelog 问题）。把写入位置从顶部挪到末尾解决不了任何事。
2. 唯一把冲突面归零的写法是**一条一文件**（`<date>-<slug>.md`）：不同文件名永不冲突。文件名含日期则字典序即时间序，`ls` 即索引，无需生成器也无需人工归拢环节。
3. 存量不必迁移：老文件原地冻结为只读区，检索用 `git grep <词> -- old.md entries/` 一条命令跨新旧。迁移是零收益的 diff 噪音。

## 副产坑：合并实验自己也会静默作废

实验脚本里 `git checkout master` 在默认分支为 main 的仓库静默失败（报错混在输出里、脚本继续跑），后两组分支从上一组分支尖切出成**祖先关系**——`merge-tree` 对祖先必然「无冲突」，整组结论无效，且方向恰好与想要的结果一致，极易照单全收。**合并类实验先跑 `git merge-base --is-ancestor A B` 断言基点独立，再采信结果。**

## 适用判据

任何「所有人往同一文件的同一位置加行」的文件都适用：changelog、反例库/坑清单、每周记录、手写注册表（后者更优解是按目录自动发现）。反之，低频写入或单人维护的文件不值得拆。
